# A100-40G 集群 Token 产能:实测、推导与被证伪的结论

> 硬件:2 节点 × 4×A100-PCIE-40GB / 鲲鹏 ARM64 / 节点内 PCIe 无 P2P / 节点间 RoCE / 每节点 251 GB 内存
> 模型:`DeepSeek-V4-Flash-0731`(167 GB,路由专家 FP4,注意力与共享专家 FP8)
> 需求:1000 亿 token/天(**用户确认**);售价 1.35 / 4.05 元/百万(**用户确认**);成本 2.00 元/卡时(**用户确认**)
>
> 标注:`[实测]` 本文实验所得 · `[推导]` 由数据推算 · `[证伪]` 曾经的结论,已被实测推翻
>
> ⚠️ **本文所有 TPOT 数字都是「每 SSE chunk」,不是「每 token」。** 投机解码下
> 一个 chunk 携带约 2.7 个 token(DSpark 接受长度),所以真实的每 token 间隔约为
> 所列值的 1/2.7。TTFT 与 tokens/s/卡 不受影响(前者是首 chunk 时刻,后者取自
> 服务端 `usage.completion_tokens`)。该口径问题由外部仓的「测量陷阱」清单点出。

---

## 0. 已被实测推翻的结论(先看这个)

| 曾经的判断 | 实测结果 |
|---|---|
| 输入:输出 = 8:1(需求文档所拍) | **计费 100:1,算力 22.8:1**,差一个数量级 |
| 提高 `--max-num-seqs` 到 64/128 能 +14~23% | **b=64 比 b=32 慢 31%**;b=128 起不来。32 已是最优 |
| `VLLM_PP_LAYER_PARTITION=24,19` 有 +5.7% | 真实流量形状下**反而慢**(370.3s vs 353.0s)。那 +5.7% 只在假形状 8288:1024 上成立 |
| 批预算 2048→8192 能救冷 prefill | 只快 2~5%。瓶颈是 kernel,不是批预算(§4) |
| 「V4.1 把 KV 压缩了很多」 | **反的** —— 0731 的 `compress_ratios` 是 4/128,V4.1 是 2/1(§8) |
| 「用 4 节点跑 V4.1 就不用分流了」 | V4.1 在本硬件**根本跑不起来**(三个结构性约束,§8.1) |
| 冷启动 110s 是个普遍问题 | 那是最坏情况。真实流量**中位冷 TTFT 仅 0.1s**,只有 8.4% 的请求 >20s(§7.1) |
| TP4 节点内是唯一选择 | **TP2×PP4 吞吐 +51.6%**,冷 prefill +30~66%(§3.6) |
| 外部仓的 `ROW_CHUNK=64` 修复必须采纳 | 那个崩溃在本 fork **不复现**;64 还慢 6%(§3.7) |
| 外部仓的 EP 否定结论(72σ)适用于我们 | **反的** —— 我们开 EP 快 17.2%(§3.8) |
| 900k 深度召回崩到 30%/0% | **我的 `max_tokens=64` 截断造成的假象。给足预算后 862k 深度 10/10 全中**(§3.9) |
| 随机文本会虚高吞吐 ~35% | 方向反了,自然文本还略快(§3.9) |
| 「8 台机器 rail2 坏了 / 只有 2 条轨可用 / metric 决定可达性 / SDN 没下发端口-IP 绑定」 | **全部作废。RoCE 从没坏过 —— 55 台 × 4 轨 RDMA 全部线速 11.4~11.7 GB/s。是我拿 ping 当健康判据,而 ICMP 与 RoCEv2(UDP/4791)是两条策略路径(§7.4.1)** |
| 合成基准上 TP4×PP2 的 decode 每卡快 36%,该换回去 | **真实形状下反而慢 22.1%**(计费 2409.9 vs 3092.5 tokens/s/卡),轮0 TTFT +49.6s。合成基准的输入:输出是 2.5:1,线上是 100:1(§3.6.1) |
| `--max-num-batched-tokens` 提到 8192 能提吞吐 | 1M 下**装不下**(需 5.07 GiB > 可用 5.06 GiB,启动失败);4096 能装但 −1.7% 且吃掉 41% KV 池(§3.6.1) |
| 卸载缓冲区实用上限是 150 GiB | **上限是 `cudaHostRegister` 的注册次数(约 4.5 万次/进程),不是固定 GiB 数。** 它随 chunk 大小变,而 chunk 大小随并行配置变。本配置下 150 GiB 需 70,595 次,实测失败(§3.3) |
| 投机解码 `num_speculative_tokens` 从 5 降到 3 有 +5.8% | 真实形状下 **−0.2%**,噪声下限的 1/27。那 +5.8% 来自合成基准(§3.6.1) |
| GPU KV 池越大命中率越高 | **无关。** KV 池小 20% 时命中率完全相同(79.5% vs 79.4%)—— 淘汰的前缀落到宿主内存那层,重入 2.79s vs GPU 热态 2.70s(§3.10) |
| `X-GPUStack-Model-Instance` 是给客户端用来钉实例的,网关剥离它是多余的安全措施 | **方向整个是反的。** 它是「网关 → worker」的输出;网关的 `weighted_clusters` 不读任何客户端头。放开剥离后 **6 次请求 3 次 404**,把静默的性能问题换成了显性的可用性故障(§7.2.1) |
| 同事那台累计命中率 89.3%,说明 4 副本下不做亲和也能高命中 | **累计值会骗人。** 同一套受控回放打上去只有 32.0%,和我们未生效时的 34.1% 一个水平。累计值混了历史上副本数更少的时期(§7.2.1) |
| 重启 gpustack server 无影响,它不在推理数据路径上 | **会拆掉运行中的实例。** server 一断,worker 的 orphan 清理把运行中的从节点当孤儿拆除,而 PP 主节点十几分钟内察觉不到,下一个请求直接崩。实测一个副本 40 分钟不可用(§7.2.2) |
| 网关多出来的那 1.77 秒是本地 token 计数,计费必须计数所以省不掉 | **是内容审核,跟计费计数毫无关系。** 计数走的是逐 rune 状态机,亚毫秒级。转发本身恒定 0.1~0.2s、不随 prompt 大小变化。关掉审核后 23k 的网关开销从 1.760s 降到 0.098s(§7.2.3) |
| 加副本能线性增加计费产能 | **做亲和之前是次线性的,加副本反而掉。** 3 副本命中 48.5%、4 副本 34.1%,总计费产能 5.8 → 6.1:多 33% 的卡换来 5% 的产能。亲和的真实意义是「让扩容重新变得有意义」(§3.4.1) |
| `--max-num-seqs=32` 在任何上下文下都是虚的 | **23k 短上下文下它是实的,而且正好是拐点。** 32 以上吞吐一个 token 不涨(113.8 → 113.1 → 113.9),TTFT 从 7.00s 涨到 72.71s。§3.4 那句结论只对长会话成立(§3.4.1) |
| 热态每卡计费产能是冷态的 8.8 倍 | **是 1.93 倍。** 8.8 倍是我自己算错的:`prompt_tokens` 本身已是计费量,我又乘了一遍 `1/(1−命中)`。同时「实算吞吐也涨了」也是错的 —— 热态算力反而只有冷态的 **0.42 倍**(4,336 对 10,261):同一秒收近两倍的钱、只算四成的活(§3.4.2) |
| 并发越高会摊薄前缀缓存命中率 | **只要不撞 KV 池天花板就不摊薄。** 23k 形状下并发 1→64 命中率恒定 78.0~78.1%(§3.4.2);但混合形状 conc=32 时活跃上下文 5.6M 超过 3.6M 的池,命中率掉到 73.4%、计费吞吐降 19%(§3.4.3) |
| 运行点定在 conc=32(`max-num-seqs`) | **只对 23k 均匀形状成立。混合真实形状下运行点是约 2,32 是最差的点** —— 吞吐低于 16 档、TTFT p90 到 637 秒。同一延迟预算下可用并发从 32 掉到 2,**差 16 倍**,代价全来自大文档冷首轮(§3.4.3) |
| 引擎被堵死时能从 `num_requests_running` 看出来 | **看不出来。** 一个大 prefill 吃满 batch 预算时 running = **1**、抢占 = 0、无 5xx,而请求在队列里等到 305 秒超时。要看 `num_requests_waiting`(§3.4.5) |
| 「PD 分离不是被带宽卡死的,RoCE 有 50 GB/s」 | **是我自己引错了数。** GPU-Direct 确实被硬件挡住(ACS 启用在 11/19 个 PCI 桥 + 跨 NUMA,只能 BIOS 层解)。50 GB/s 是标称推算,实测多卡 19.61 GB/s;且那张表只算 RDMA 一段、漏掉两次 PCIe 搬运。端到端余量是 **5.6~15 倍**而非一到两个数量级(§7.4 纠正框、§3.4.4) |
| 供应商在 1M 这种体量上大概留不住前缀缓存 | **三家全是 99.9% 命中。** 950k 首轮后的续写:我们 TTFT 7.8s、火山 9.0s、并行 8.2s。缓存能力不是差异化,差距全在冷首轮 —— 它们 61s、我们 185s,快 3 倍(§3.9.1) |
| 那 20ms 是 CUDA graph 没生效、kernel launch 开销 | **graph 是生效的,而且消掉了约 185ms。** eager 的 step 是 212.8ms、graph 是 27.3ms(7.8 倍)。剩下的是 **GPU 真的在执行 kernel**:上千个 `6×4096×2048` 的微型专家 GEMM,占用率受限 —— 专家数 34→229(6.7 倍工作量)kernel 时间只涨 1.91 倍(§3.6.4) |
| 解码慢是撞了 A100 的显存带宽 | **只用到 22%**(conc=16 时 339 / 1555 GB/s)。瓶颈是**每 step 约 20ms 的固定开销**:26.3ms 的 step 里约 2ms 搬权重、约 6ms 一次 PP 跨界、剩 20ms 说不清去处(§3.6.4) |
| `vllm:estimated_read_bytes_per_gpu` 能用来判访存瓶颈 | **它只统计注意力层,不含 MoE 权重**(`v1/metrics/perf.py:470`),而本模型是 MLA、KV 极小。实测 4.7~19.5 GB/s 且随并发**下降** —— 拿它判 MoE 会得出完全错误的结论。FLOPs 估计器对 `deepseek_v4` 没注册,恒为 0(§3.6.4) |
| 解码几乎没有批处理收益(TPOT 随并发线性涨) | **指标选错了。** TPOT 是「固定 step 速率被 N 个流分摊」的结果,它随并发涨是正确行为。看 step 耗时才对:conc 1→4 的 step 耗时完全没变(26.3 → 25.9ms)、吞吐翻倍,**批处理是完美的**(§3.6.4) |
| 聚合解码封顶 141 tok/s,与百度差 5 倍 | **那不是解码上限,是 prefill 抢 batch 预算。** 纯解码负载下同一配置到 **513.8 tok/s**(3.6 倍)。141 是「30k 文档 + 每轮追加 2k」形状下两者争抢 2048 预算的结果。与百度的差距是 2~4 倍且取决于负载形状(§3.6.4) |
| 减少 TP 是通用优化(§3.6 的结论) | **只对冷 prefill 成立,对解码是反的。** 解码时 batch 极小、all-reduce 载荷只有百 KB,PP 的串行化才是主要成本。TP4×PP2 比 TP2×PP4 的 TPOT 好 **18~33%**(收益随并发递增),已在现网生效。而 TP8×PP1 反而差 2.4 倍 —— TP 的成本是每次前向 86 次集合通信的**延迟**,不是带宽(§3.6.2) |
| 批预算 2048 把解码饿死了 | **否。** 2048/4096/8192 在噪声内,2048 在 16 并发还略好。九个配置里只有拓扑一个变量真的有效(§3.6.2) |
| 投机解码占着调度预算,关掉能提升并发解码 | **反了。** 关掉 TPOT 差 1.35~2 倍(conc=1:18.4 对 10.0ms),它是刚需。引擎那条「批预算因投机解码被钉在 2048」的警告指向的不是解码扩展性(§3.6.2) |
| 供应商在 1M 体量上留不住前缀缓存 | **四家全是 99.9% 命中。** 缓存能力不是差异化,差距全在冷首轮:百度 33.6s、火山 61.4s、我们 185.5s(§2.5) |
| 1M 上下文是我们对供应商的差异化 | **四家输入上限都是 1M。** 而且百度的 `max_tokens range is [1, 393216]` 是**输出**上限,不能据此推断上下文(§2.5) |
| INT8 权重能吃到 A100 的原生 INT8 张量核,是明确升级 | **8 卡上物理装不下**(312.3 GB vs 316 GB 可用,KV 一点不剩)。16 卡能装且每卡权重字节数几乎不变,但副本数腰斩 + PP 被迫 4 级(刚实测差 28~33%),净收益待测(§5.1) |
| 队头阻塞是长上下文推理的固有代价 | **三家供应商全都没有(0.7~1.0×)**,两个自建的都有(我们 7.3×、同事 2.0×)。百度 300k prefill 只要 7.6s(≈39,500 tok/s,是我们的 4 倍)。这是工程差距,不是物理限制(§3.4.4) |
| 1M 上下文是我们对供应商的差异化卖点 | **火山和并行也是 1M**(`max_model_len=1048566`)。只有同事自建(400k)和百度(384k)更低。而且 1M 首字要 200 秒(§3.9.1) |

方法论教训(按踩到的顺序,不按重要性):

1. **任何在 8288:1024 这种合成形状上得到的结论,都必须在真实形状上重验。**
2. **合成测试要用真实分位点采样,不要只测最坏情况** —— 我用 490k 全新上下文
   得出「冷启动 110s」,而线上纯输入的中位只有 892 token,两者差 550 倍。
3. **不要照搬别人在不同硬件/不同区间上的结论。** 本轮四条错误全部源于此:
   外部仓是 **8×A100 NVLink + 8K prefill**,我们是 **PCIe 无 P2P + 长上下文**。
   他们的 EP 否定、`ROW_CHUNK` 修复、kernel 开关收益,在我们这儿三条不成立。
4. **推理模型的评测必须给足输出预算。** `max_tokens=64` 让 862k 深度的召回从
   100% 读成 0%(思维链还没写完就被截断)。对齐各组预算,否则测的是预算。
5. **判据必须走要用的那条路。** 同一类错误已犯三次:`max_tokens=64` 当召回判据、
   批量 ping 超时当可达性判据、ICMP 当 RoCE 健康判据。前两次浪费时间,
   第三次更严重 —— 为一个不存在的故障重启了 6 台生产机、改了 7 台的路由。
   **要测 RDMA 就用 `ib_write_bw`,要测召回就给足预算,不要用替代信号。**
6. **合成基准的 workload 形状不匹配线上时,结论可能符号相反 —— 不是偏差,是反的。**
   同一对配置(TP2×PP4 vs TP4×PP2),合成基准(输入:输出 2.5:1、强制 cache miss)
   得出 TP4×PP2 **赢 36%**;真实会话形状(输入:输出 ~100:1、命中率 79.4%)得出
   TP4×PP2 **输 22.1%**。原因是线上的 prompt 九成被缓存省掉,真实开销集中在
   轮0/轮1 的冷 prefill,而合成基准把 decode 的权重放大了约 40 倍。
   **任何拓扑 / 调度 / 投机解码参数的决策,必须用 §3.2 那套会话形状回放复核。
   单请求或短输出的合成基准只能用来定位现象,不能用来做决策。**
7. **同一个观测有两种解释时,不能只挑符合假设的那个。** 改动前 `gwtest.py` 就已经
   测出「显式钉实例与命中结果错位」,我把它归因为「头被网关剥掉了」,而没想到还有
   「网关压根不读这个头」这个同样成立的解释 —— 后者才是真的。**验证脚本在改动前
   就跑出了答案,是我读错了。** 上线前只验证了「配置对不对」(remove 列表、单元
   测试、打包门禁全绿),没验证「行为对不对」。
8. **失败形态是静默的功能,日志必须指名道姓。** 管理 API 返回 `HTTP 200 + total=0`
   既不是认证失败也不是报错,而代码按设计静默跳过 —— 这次定位花了两小时,全靠读
   gpustack 源码倒推。补日志时措辞要直接写出答案(「说明管理密钥的作用域不对」),
   而不是只报现象(「实例列表为空」)。同时这类日志**必须节流**:
   stale-while-revalidate 的缓存会让同一条状态在整个 TTL 内每个请求都命中,
   不节流就是按流量速率刷屏。
9. **要定位延迟在哪一侧,就去看被测方什么时候开始干活,不要靠相减推断。**
   我一开始拿「本机经公网 6.99s」减「集群内直连 1.97s」,得出「网关慢 3.5 倍」——
   两个数的客户端位置都不同,根本不可比。正确做法是同一客户端位置发两条路径,
   再轮询实例的 `num_requests_running` 看它何时被唤醒(§7.2.3)。**排除传输的
   便宜办法:用不存在的模型名发同样大小的 body,请求在推理前被拒,剩下的就是
   纯传输。**
10. **压测用唯一内容,测出来的全是「首轮」。** 那条网关开销的尺寸曲线每个请求
    内容都唯一,于是每一个都付了完整的审核成本,结论看起来是「所有请求 +1.7s」。
    换成真实多轮回放才发现**只有首轮贵,后续几乎免费**(§7.2.3)。同理,§3.4.1
    的并发拐点是 0% 命中下测的,不等于现网 78% 命中时的可卖容量。
    **做容量结论前先问自己:我造的缓存状态和现网一样吗?**
11. **长 prompt 的字符/token 比必须用 `/tokenize` 校准。** 实测中文语料是
    **1.7391 字符/token**,按 2.0 估会差 15%。8k 上无所谓,逼近 1M 时会直接
    撞 `max_model_len` 或测错长度档(§3.9.1)。
12. **平均值会藏掉整类故障。** 并行那个请求 TTFT 只 5.1s、端到端 175.9s ——
    解码中途卡了 170 秒。平均解码速率完全看不见,必须看交付间隔的尾部(§2.4)。
    另外投机解码(`dspark`,5 token)让一个 SSE chunk 带多个 token,
    **chunk 间隔不等于 token 间隔**,两个指标要分开报。
13. **算「计费 tokens/s」之前先确认 `prompt_tokens` 是哪一边。**
    `prompt_tokens` **已经是计费量**(含命中的部分),算力量是 `prompt_tokens −
    cached_tokens`。我在 §3.4.2 里把前者标成「实算」又乘了一遍 `1/(1−命中)`,
    于是每卡计费虚高 4.55 倍(11,255 实为 2,470),还顺手为这个假数字编了一条
    机制解释(「实算吞吐也涨了」)—— 而真相相反,算力降到 0.42 倍。
    **数字错了会自己长出解释来**,所以业务口径的指标要先把定义写进文档再算
    (§3.4.2 开头那三行就是为此加的)。
14. **重尾分布上,小样本的均值毫无意义。** 混合形状扫描第一版每档随机抽 6~12 个
    文档尺寸,结果各档平均 prompt 是 189,973 / 43,256 / 87,234,差 4 倍 ——
    于是 conc=1 反而比 conc=4 吞吐高。那是抽样噪声,不是并发效应。
    改成**分层采样**(u=(i+0.5)/N 过分位函数)并让每档跑完全相同的一组会话,
    档位之间才可比(§3.4.3)。§1.2 的 P99 是 895k 而中位是 39.5k,
    这种尾巴下随机抽样需要几百个样本才收敛。
15. **先确认「你改的文件」和「正在跑的文件」是同一个。** 下载脚本在管理节点上
    连续三轮都是同一个 `Exit 127`,我却一直在加固「缺 flock」这个方向。真相是
    **`/nfs-data` 是符号链接(`→ /nfs-models/wuhanjisuan894`)不是挂载点**,管理
    节点没挂 `/nfs-models` 时它指向别处 —— 跑的根本不是我改的文件。
    **「加了一堆报错分支,输出却一字未变」本身就是最强的信号**,当时就该去核 md5。
16. **不要吞错误。** 同一个脚本里 `2>/dev/null` 让两件事各花了两个来回:manifest
    取源失败后静默回退到慢源(23.7 对 105.1 MB/s),以及前置检查失败只剩一个
    光秃秃的 127。**失败路径的可观测性和成功路径一样重要** —— 现在 HTTP 码、
    curl 错误、解析异常全部进日志。
17. **改了源/依赖之后,要在「实际运行的那台机器」上验,不是在你手边那台。**
    魔搭源在计算节点 32.3 MB/s,在管理节点取 manifest 直接失败 —— 我只在
    gpu21 上验过就让对方重启了,那次重启是白做的(而且丢掉了已建好的连接,
    速度从 23.7 掉到 18.5)。
18. **输入上限和输出上限是两个数,不能互推。** 百度的 `max_tokens range is
    [1, 393216]` 是输出上限,我据此推断它上下文 384k —— 实际输入上限是 1M(§2.5)。
19. **量化仓选基座要逐字段比 config,不能看名字。** `Intel/DeepSeek-V4-Flash-
    W4A16-AutoRound`(无 `0731`)基于预览版、三个 `dspark_*` 字段全缺,下载量还
    比对的那个高。选错的表现是「莫名其妙地慢」而不是报错(§5.1)。
20. **改配置之前,先问「引擎已经告诉我什么」。** 定位解码瓶颈用到的四个计数器
    (`iteration_tokens_total`、`generation_tokens_total`、`spec_decode_num_*`)
    **`/metrics` 里一开始就有**,不用改代码也不用重启。我却先扫了九个配置、
    调研了五个量化候选、下了 163 GB 权重,才回来看它们 —— 而它们一上手就推翻了
    两条我已经写进文档的结论(§3.6.4)。
21. **区分「结果指标」和「原因指标」。** TPOT 是结果(step 速率 ÷ 并发数),
    step 耗时才是原因。拿结果指标当判据,会把正确行为误读成病理 ——
    我据此编出了「批处理零收益」并为它找了四个机制解释,九个配置全是为验证
    这个错前提而跑的(§3.6.4)。
22. **合成语料会系统性压低投机解码的接受率。** 我的 prompt 是随机中文词拼的,
    草稿模型无法预测随机串,实测接受率只有 45~48%。**本文档所有 TPOT 与解码
    速率对真实流量都偏悲观**,拿准数必须用线上语料重测(§3.6.4)。
23. **一个端点上只能有一个压测客户端。** 实例启动失败后我在同一端口重开,
   而上一轮的 poller 还在轮询,于是两个客户端同时发压 —— 并发翻倍、TTFT 从
   4.75s 读成 103.44s,整组数据作废。重开必须换端口,或先确认旧 poller 已退出。
   并行测多臂时**每臂配一个独立客户端节点**:一个 Python 进程驱动 24 路
   19 万 token 的 SSE 长流,客户端自己就是瓶颈,测出来的 TTFT 全是排队时间。

#### 我们真正的短板:解码差 2.5 倍

输出中位都是 256 token、同样 8 并发。这是跨节点 PP 的代价:每个 token 过一次网络。
百度端到端赢 1.76 倍全靠解码,它 TTFT 其实比我们差。

**能不能平替百度?算平衡点:**

```
我们:  0.91s + N × 20.4ms      (TTFT 用关掉审核后的值,见 §7.2.3)
百度:  1.34s + N ×  8.0ms
相等 → N ≈ 35 token
```

**输出超过约 35 个 token 百度就更快。** 而 V4-Flash 带思维链,`reasoning_content`
动辄几百 token —— 所以**几乎所有真实交互场景都落在百度更快的那一侧**。

- 现在就能平替:**长文档 + 短答案**(抽取、分类、判别、路由、简短问答),以及

注意**不是简单「缩上下文换解码」就能补上** —— 同事那套 400k 配置的解码是
37.9 tok/s,比我们 1M 配置还慢。要动解码得单独做实验。

## 3. KV 卸载:本项目最大的单项优化 `[实测]`

### 3.1 淘汰重入测试

GPU KV 池 638,912 token,一个 490k 上下文即可挤掉另一个。

| 步骤 | TTFT |
|---|---|
| A 首次(冷) | 106.34s |
| A 再次(GPU 热) | 2.70s |
| B、C 各 490k 把 A 挤出 GPU | 106.72s / 107.61s |
| **A 被挤掉后重来** | **2.79s** |

**被彻底淘汰的会话重新命中只要 2.79s,比重算快 38 倍。**

原因:我们 prefill 慢(4.5~7.5k tok/s),而 KV 搬运走 host→GPU 的 PCIe(不受无 P2P 影响,~20 GB/s)。**搬 KV 比重算 KV 快两个数量级。**

| 基线(无卸载) | **1332.3s** | — |
| **开卸载 100 GiB** | **357.0s** | **2380.1** |

**3.7 倍。** 另外两台机器的交叉验证:gpu49+50 卸载 100 GiB → 353.0s / 2407.2;
gpu45+47 卸载 + `PP_LAYER_PARTITION=24,19` → 370.3s / 2295.1(PP 分区**变慢**)。

逐轮 TTFT:

| 轮 | TTFT 中位 | 最大 | 平均 prompt |

### 3.3 卸载缓冲区大小

默认后端是 `/dev/shm`,上限为宿主内存的一半(实测 134.6 GB free)。超过就报:

```
/dev/shm has 134.6 GB free but the KV offload region needs 193.3 GB
... or set VLLM_KV_OFFLOAD_REGION_BACKEND=memfd
```

`memfd` 后端可突破 `/dev/shm`,但会在 `cudaHostRegister` 处撞墙。

**墙是注册次数,不是字节数,也不是剩余内存 `[2026-09-15 修正]`**

原先这里写的是「实用上限约 150 GiB」。那个数字只在当时那组 chunk 大小下成立,
不是通用上限。三次实测:

| flag | chunk 大小 | 总 chunk 数 | 结果 |
|---|---|---|---|
| **75**(现网) | 2.28 MB | 35,297 | ✅ `pinned 35297 chunks in 35297 registrations (10.06 GB)` |
| 150 | 2.28 MB | 70,595 | ❌ rank0 死在 59365、rank1 死在 45452 |
| 300 | 2.28 MB | 141,190 | ❌ 死在 49419 |
| 200(旧配置) | 4.19 MB | 51,200 | ❌ 死在 41270(≈161 GiB) |

失败点全部落在 **4.1~5.9 万次注册**,而 chunk 大小差 1.8 倍、失败时的已注册字节
从 56 GB 到 173 GB 不等。失败时宿主机 251 GiB 里还空着 176 GiB —— **和内存余量无关**。

```python
# vllm/v1/kv_offload/cpu/spec.py:104-120
num_copies = 1 if replicated_layout else world_size
kv_bytes_per_chunk = worker_kv_bytes_per_block * num_copies * blocks_per_chunk
num_chunks = int(cpu_bytes_to_use) // round_up(kv_bytes_per_chunk, BLOCK_SIZE_ALIGNMENT)
```

`chunk` 大小由 `world_size`、`blocks_per_chunk`、每 block 的 KV 字节共同决定,
**换并行配置就会变**。所以可填的最大 GiB 也跟着变:

```
可填上限 ≈ 45,000 × chunk 大小
本配置(TP2×PP4,chunk 2.28 MB)→ 约 100 GB ≈ 95 GiB
```

**现网填 75(35,297 次注册)已经贴着天花板,没有加的空间。** 想榨到 90 也可以
(约 42,000 次),但按下表 8 会话量级的收益只有 1.4%(噪声),而撞墙的代价是
实例 pending 十几分钟后才失败,比直接报错更难排查。不值得。

> 这也解释了 §6 那句「TP4×PP2 用 150,TP2×PP4 必须减半到 75」**是对的**。
> 我曾按代码算式推断「每节点只 pin flag/2,所以能填 300」,实测 300 和 150 都失败。
> 推导输给实测。

| 卸载大小 | 8 会话 | 24 会话 |
|---|---|---|
| 100 GiB(`/dev/shm`) | 353.0s / 2407.2 | 1777.8s / **1433.9** |
| 150 GiB(`memfd`) | 348.0s / 2441.6 | 1561.0s / **1632.6** |

**低并发下没区别;24 会话时 150 GiB 快 13.9%。** 容量只在超订严重时才兑现。

### 3.4 并发会话数:约束是延迟,不是吞吐 `[实测]`

| 会话数 | 平均上下文 | 活跃上下文总量 | 超订率 | tokens/s/卡 | 第2轮(热)TTFT 中位 |
|---|---|---|---|---|---|
| **8** | 172k | 1.38M | **2.2×** | **2441.6** | **3.2s** |
| **12** | 130k | 1.56M | **2.4×** | 2132.6 | **1.2~2.4s** |
| 16 | 166k | 2.76M | 4.3× | 1796.7 | **56~73s** |
| 24 | 172k | 4.14M | 6.5× | 1632.6 | **157.3s** |

超订率 = 活跃上下文总量 ÷ GPU KV 池(638,912)。**以上全部在 TP4×PP2 下测得。**

换成 TP2×PP4 后悬崖大幅后移(自然文本语料):

| 拓扑 | 会话 | tokens/s/卡 | 后段(热)TTFT 中位 |
|---|---|---|---|
| TP4×PP2 | 16 | 1796.7 | **56~73s** |
| **TP2×PP4** | **16** | **3271.2** | **2.2~2.5s** |
| **TP2×PP4** | **8** | **3773.2** | **1.4~2.2s** |

**同样 16 会话,换拓扑后 TTFT 从 56~73 秒降到 2.2~2.5 秒,吞吐还高 82%。**
所以「16 会话就过悬崖」只对 TP4×PP2 成立;**TP2×PP4 的甜点是 8~16 会话**。

两条仍然成立的结论:

1. **吞吐随会话数单调下降**(8 会话最高)。**加会话只买到延迟,买不到吞吐。**
2. **约束是延迟,不是吞吐。** 定运行点要看 TTFT 的 SLO,不是看 tokens/s。

`--max-num-seqs 32` 在长上下文下是虚的:32 个 170k 会话需要 540 万 token 的 KV,
调度器实际只放行约 3~4 个,其余排队 —— 所以必须在**网关**侧限流,靠引擎参数拦不住。

`[推导]` **网关准入规则**(用 token 总量而非会话数,因为上下文跨度极大):

```
TP4×PP2: 活跃上下文总量 ≤ 2.2 × KV池 ≈ 1.4M token  → 8~9 个长会话
TP2×PP4: 实测 16 会话(约 2.2M token)仍然健康 → 上限至少 16 个长会话
```

中位 39.5k 的小会话可到 32 个(被 `max-num-seqs` 封顶)。

#### 加副本是不是线性?

**原始吞吐:接近线性。** 副本之间不共享 KV 池、不共享显存,§3.3 那个
`cudaHostRegister` 注册数墙是 per-process 的。

**但计费吞吐在做亲和之前是次线性的 —— 加副本反而掉:**

| 副本数 | 命中率(无亲和) | 每卡计费乘数 | 总计费产能 |
|---|---|---|---|
| 3 | 48.5% | 1.94× | 3 × 1.94 = 5.8 |
| 4 | **34.1%** | 1.52× | 4 × 1.52 = **6.1** |

**加了 33% 的卡,只换来 5% 的计费产能。** 因为无亲和时会话下一轮落到「持有它前缀
那台」的概率是 1/N,N 越大越低。做完亲和后命中率不再依赖 N(HRW 保证同会话恒定
落同一台),4 副本 × 4.63× = 18.5,再扩容才是等比例往上走。

**所以亲和特性的真实意义不是「提升 2 倍」,是「让扩容重新变得有意义」。**

三个不线性的地方:

1. **每次扩容有一次性代价。** HRW 加一个实例会重映射 1/(N+1) 的会话,这批会话的
   缓存白丢一次(N=8→9 是 11%)。**不要频繁扩缩容。**
2. **单会话延迟一点不改善。** 加副本买的是并发,不是速度。
3. **new-api 和 Higress 是单点,从没测过。** 每个 23k 请求的 body 是 234 KB
   (中文 UTF-8 三字节 + JSON 转义),副本到几十个以后瓶颈会从 GPU 挪到网关。

### 3.4.2 热态并发扫描:可卖容量,运行点定在 32 `[实测 2026-09-15]`

### 3.4.3 混合真实形状:运行点是 2,不是 32 `[实测 2026-09-16]`

|---|---|---|
| 纯小/热(23k,§3.4.2) | **32** | 1.72s |
| 混合真实形状 | **~2** | 约 5s |

**混入大文档冷首轮的代价是 16 倍并发。** 这是「不分流」的价格,也是 §7.1
那条「超大文档首轮 → 供应商」的定量依据。

> ⚠️ 用 23k 均匀形状定运行点会得出 32,实际混合流量下 32 是**最差**的点
> (吞吐低于 16 档、p90 到 637 秒)。这是本文档第二次同类教训 ——
> 第一次是「唯一内容压测测出来全是首轮」(§0 方法论第 10 条)。

### 3.4.4 队头阻塞:四家对比 `[实测 2026-09-16]`

上一节的排队公式指向一个具体机制:`--max-num-batched-tokens=2048` 下,
一个大 prefill 吃满整个 batch 预算,后面的请求一步都推进不了。用一个更锐利的
实验隔离它 —— A:8 个 23k 小请求并发;B:先起 2 个 300k 大请求,2 秒后发同样的
8 个小请求。小请求 TTFT 的恶化倍数就是阻塞强度。300k 是因为百度上限 384k。

| | A 小请求 p50 | B 小请求 p50 | **p50 恶化** | p90 恶化 | 300k 大请求自身 | 折合 prefill |
|---|---|---|---|---|---|---|
| 我们(1M,直连单副本) | 9.62s | 70.56s | **7.3×** | 5.5× | 32.0s / 63.6s | ~9,400 tok/s |
| 同事(400k,经网关 4 副本) | 7.09s | 14.47s | 2.0× | 5.5× | 54.6s / 64.1s | ~5,500 tok/s |
| 火山 | 2.14s | 1.90s | **0.9×** | 0.9× | 13.8s / 13.4s | ~21,700 tok/s |
| 并行 | 2.37s | 2.40s | **1.0×** | 0.6× | 15.9s / 15.1s | ~18,900 tok/s |
| **百度** | 2.05s | **1.42s** | **0.7×** | 0.8× | **7.6s / 7.8s** | **~39,500 tok/s** |

**三家供应商全都没有这个问题(0.7~1.0×),两个自建的都有。** 小请求在两个 300k
并存时甚至略快(噪声内)。而且它们的大 prefill 快得多:百度 300k 只要 7.6 秒
≈ 39,500 tok/s,是我们的 4 倍。基本只能是 **PD 分离**(prefill 与 decode 在不同
池子)加足够大的机队。**这是工程差距,不是长上下文推理的物理限制。**

#### ⚠️ 不要把「PD 分离」和「按大小分流」当成一回事

供应商很可能用的是 PD 分离,但**修我们这个阻塞不需要它**。两件事完全不同:

| | PD 分离 | 按大小分流 |
|---|---|---|
| 做什么 | **同一个请求**的 prefill 与 decode 在不同实例,中间传 KV | **不同请求**去不同实例,每个实例仍自己做完整 prefill+decode |
| 需要跨实例传 KV | 是 | **否** |
| 改哪里 | 引擎 + connector + RDMA | **只改网关路由** |
| 解决队头阻塞 | 是 | **是** |
| 提升 prefill 速率 | 否 | 否 |

**大 prefill 只堵同一副本上的请求。** 大文档首轮不落在服务小/热请求的副本上,
那些副本就永远见不到大 prefill。现有亲和代码正好是落脚点:加一条「首轮且
prompt > 200k → 池 B」,之后亲和把该会话一直钉在池 B(缓存在那儿),语义自洽。

**那 PD 分离本身可行吗?余量比想象的薄,而且路径是被硬件限定的。**

- **GPU-Direct(GDR)确实被硬件挡住**(§7.5):`nvidia-smi topo -m` 显示
  GPU ↔ NIC 全是 `SYS`(穿 PCIe + 跨 NUMA),19 个 PCI 桥中 11 个启用了 ACS,
  ACS 会阻断 peer-to-peer DMA。加载 `nvidia_peermem` 后内存注册能过,数据仍传不
  过去。只能在 BIOS / 启动参数层解(`pcie_acs_override`)——**运维决策,不是改代码**。
- **没有 GDR 也过线,但只有 5.6~15 倍,不是一到两个数量级。** §7.4 那张表里的
  「4×100G 齐上 50 GB/s」是 4 × 12.5 的**标称推算**,§7.5 实测多卡只有
  **19.61 GB/s**;更关键的是那张表**只算了 RDMA 那一段,漏掉两次 PCIe 搬运**。
  §7.5 自己做了诚实的账:12.5 GB 走 GPU→主机→RDMA→主机→GPU 合计约 **2.2s**,
  对重算 12.3s 是 **5.6×**;1M 会话(75 GB)约 13.6s 对重算 200s,约 **15×**
  (重算超线性,上下文越大越划算)。
- 而且这是一次 `transfer_engine_bench` 的点测,**没有在真实 KV 搬运路径上验过**。
  要做 PD 分离,这个余量必须自己重测。
- 软件侧另有两个坑:`nixl` 我们故意没装(§7.8),`mooncake` 写路径每个 key
  都失败(§7.7.1)。

**但即使全部打通,PD 分离也不该是解决队头阻塞的路径**:它把传输加在关键路径上
(大请求仍要 200s prefill,再加 13.6s 传输,单个请求不会变快),它的收益是让大
prefill 不占服务池 —— **而按大小分流零传输成本就能拿到同样的收益**。

**分流不能解决的那一半:** 它不会让我们的 prefill 变快(300k 冷:我们 32~64s,
百度 7.6s)。那一段只有三条路 —— 预热移出关键路径(§7.3)、买供应商的(§7.1)、
或者真做 PD 分离 + 提升 prefill 并行度。

> 💰 **「大文档首轮给供应商」有一笔 §7.1 写的时候没算的账**:§1.2 说 >200k 的
> 请求占 32% 的量、却占 **83.6% 的计费额**。把这一类让给供应商 = 让出 83.6% 的
> 收入。留在自己池子里、用预热藏延迟,才是保住收入的版本。

> 并行这条第一次跑时挂了 23 分钟(A 阶段就没出来,而单个小请求 2.1s 正常),
> 把单请求超时从 3600s 压到 240s 后重跑,8/8 干净通过 —— **没能复现**。
> 与 §2.4 那个 175.9s 的长尾可能同源,按未复现的观测记,不作结论。

同事那套 `max-num-batched-tokens` 更大(400k 上下文不必配 2048),**中位恶化
只有 2.0× 而不是 7.3×** —— 大 chunk 让同一个 step 里能挤进别的 prefill。
但 **p90 恶化两边都是 5.5×**:运气差的那批照样等满全程。**大 chunk 救中位,
不救尾部。**

> ⚠️ 这个对比有 confound:同事那条走网关摊到 4 副本,两个大请求最多占 2 台;
> 我们那条直连单副本,全砸一台。我们经网关的重测被自己的压测污染了
> (`ok 4, err 4`,详见 §3.4.5),**尚未补测**。

### 3.4.5 副本被堵死时,引擎侧毫无异常信号 `[实测,一次自伤事故]`

上面两节压测期间,经网关发的 8 个小请求里有 4 个在 **305 秒后超时**,
`-1.0s` 无首字、输出 0。定位结果值得单独记:

- **不是"生成得慢",是从没被调度。** 它们落在正在跑 §3.4.3 conc=16 的那台副本上
  (该档 p90 = 238s),一直在引擎队列里。
- **引擎侧看不出任何异常。** 全程 `num_preemptions_total = 0`、无 5xx,
  `num_requests_running` 是 **1**(被一个大 prefill 占着),而
  `num_requests_waiting` 是 3。**用 running 做健康判据会完全看不到这种饱和。**
- **`RELAY_TIMEOUT` 代码默认是 0(永不超时)**,305s 是部署里显式配的。
  配 0 会让请求永久挂住,所以 300 是对的 —— 但实测混合形状 conc=16 的
  p90 已经 238s,阈值形同虚设。**这个值应该按准入控制的目标反推,不能拍。**
- **会话亲和会放大这件事。** 亲和按会话身份钉实例、**不看负载**,所以一个用户的
  会话钉在被堵住的那台上会**连续**超时,而随机分流只是偶尔一次。
  **亲和把偶发故障变成了针对单个用户的持续故障** —— 这是 §7.2.1 那个特性
  没考虑到的副作用。

`[待实施]` **准入控制的设计要点**(§3.4 只说了「必须在网关做」,这里补判据):

1. **判据不能用 `num_requests_running`**(饱和时它是 1)。要用
   `num_requests_waiting` + 排队 token 总量。
2. **过载时按 HRW 顺序取下一个候选**,而不是直接回退网关 —— 保留确定性,
   同一会话在同样负载下仍落同一台,恢复后回到首选。
3. **快速 503 严格优于排队**:305 秒后失败等于用户等 5 分钟、我们还可能已经开始
   算了。但拒绝只在「有别处可去」时有价值,且重路由会丢掉会话前缀(冷请求 +
   丢掉 4.55× 的计费乘数),所以**分流(§7.1)才是消病因的那一层,拒绝是兜底**。
4. **过度放行直接减少收入,不只是伤延迟**:§3.4.3 里 conc 16→32 多收 16 个并发,
   计费吞吐**降 19%**、算力还多烧 5%。所以准入控制是毛利项,不是纯 SLO 项。

## 3.6 拓扑:减少 TP 是冷 prefill 的大杠杆 `[实测]`

线索来自外部仓 [`allover326/deepseek-v4-cmp170hx`](https://github.com/allover326/deepseek-v4-cmp170hx):
在无 P2P 的 PCIe 上,TP 每次前向要做 `2 × 43 = 86` 次 all-reduce,而 PP 每个 stage
边界只搬一次 hidden states。他们在 **PCIe Gen2 x4** 上测到 PP4 比 TP4 快 **6.6 倍**。

我们此前**一直是 TP4 节点内**,从未试过减少 TP。同样 8 张卡:

| 拓扑 | 40k 冷 | 140k 冷 | 490k 冷 | KV 池 |
|---|---|---|---|---|
| TP4×PP2(原配置) | 5.36s / 7,516 | 19.32s / 7,297 | 104.7s / 4,710 | 638,912 |
| **TP2×PP4** | **4.12s / 9,793** | **12.41s / 11,370** | **63.25s / 7,798** | 674,060 |
| 提升 | **+30%** | **+56%** | **+66%** |

**冷 prefill 快 30~66%,490k 从 105 秒降到 63 秒。** 幅度小于他们的 6.6× —— 因为
我们是 PCIe Gen4 x16(带宽约 10 倍),TP 的通信惩罚本来就轻得多。

`TP1×PP8` 起不来:`No available memory for the cache blocks`。TP1 时每卡要独自承担
全部 8192 token 的激活(无 TP 分片),显存不够。用批 2048 可重试,但 TP2×PP4 已够用。

### 3.6.1 六个候选的全量对照:全部否掉 `[实测 2026-09-15]`

起因是和同事的线上实例(同为 8 卡跨 2 节点、A100-PCIE-40GB)正面对比,发现
**decode 每卡我们 40.2、他们 57.9(−31%)**。为定位原因,在 gpu31-40 上手工起了
五个隔离对照臂(各 8 卡、独占 2 台机器),与现网配置逐变量对比。

**配置差异(同事 vs 我们)**

**排除了「draft 质量差异」这个怀疑对象**。

### 3.6.2 九配置扫描:解码扩展性只有拓扑一个有效变量 `[实测 2026-09-16]`

§3.4.2 暴露了一个异常:**TPOT 几乎随并发线性涨**(10.2 → 110.3ms,并发 1 → 32),
**后来证明这个提法本身是错的**(§3.6.4):TPOT 随并发涨是分摊效应而非批处理失效,
而「141 tok/s」是那个工作负载下 prefill 与 decode 争抢 batch 预算的结果、不是解码
上限 —— 纯解码负载下同一配置能到 513.8 tok/s。本节的九配置对照仍然有效(它们都在
同一负载下对比),但**动机描述有误,读结论时请一并看 §3.6.4**。这一节把九个配置扫一遍找原因,每个配置独立两节点,热态形状
(30k 文档 + 每轮追加 892 token,§1.2 纯输入中位),`out=256`,并发 1/2/4/8/16。

| 配置 | conc=4 | conc=8 | conc=16 | conc=16 输出 |
|---|---|---|---|---|
| **400k / 8192 / TP4×PP2** | **23.1ms** | **39.1ms** | **57.7ms** | 141.5 |
| 400k / 8192 / TP2×PP4 | 33.6 | 54.2 | 81.1 | 130.3 |
| 400k / 2048 / TP2×PP4 | 31.9 | 53.3 | 82.9 | 142.8 |
| 400k / 4096 / TP2×PP4 | 34.2 | 52.6 | 85.9 | 138.0 |
| 1M / 2048 / TP2×PP4(原现网) | 30.9 | 53.2 | 88.0 | 132.9 |
| 无 expert-parallel | 31.9 | 49.9 | 80.4 | 132.6 |
| `num_speculative_tokens=2` | 33.6 | 51.9 | 78.3 | 127.3 |
| **无投机解码** | 38.9 | 77.0 | **111.3** | 95.9 |
| **TP8×PP1** | — | — | — | conc=2 就 31.8ms |

**四个假设被否掉:**

| 假设 | 结论 |
|---|---|
| `--max-num-batched-tokens=2048` 把解码饿死了 | **否。** 2048/4096/8192 在噪声内,2048 在 16 档还略好。引擎启动时确实警告过「`max_num_scheduled_tokens` 因投机解码被设为 2048,考虑增大」,但那条警告指向的不是解码扩展性 |
| 上下文 1M 拖累解码 | **否。** 1M 88.0ms 对 400k 82.9ms,噪声内 |
| 投机解码占着调度预算,关掉更好 | **反了。** 关掉 TPOT 差 1.35~2 倍(conc=1:18.4 对 10.0ms),它是刚需 |
| TP 越大越好(按带宽推算) | **反了,差 2.4 倍。** 我只算了带宽(11 MB/step ÷ 12 GB/s = 0.9ms),漏了**86 次独立集合通信各付一次跨节点延迟**(≈13ms)。**这是延迟问题不是带宽问题** |

**唯一有效的是拓扑。** 机制用显存带宽就能算清:模型 166.9 GB 摊到 8 卡 = 20.9 GB/卡,
A100 的 HBM 约 1.5 TB/s → 每个 PP stage 约 13ms,而**一个 token 必须串行穿过所有
stage**:

```
TP2×PP4:  4 stage × 13ms = 52ms/step
TP4×PP2:  2 stage × 13ms = 26ms/step      ← 实测改善 28~31%,量级对得上
TP8×PP1:  1 stage,但 TP 的 86 次集合通信要跨节点 → 实测反而差 2.4 倍
```

**所以最优点是「TP 顶到节点边界(TP4),PP 跨节点(PP2)」。** PP 的成本是每个
stage 边界搬一次(PP4 = 3 次),TP 的成本是每次前向 86 次集合通信 —— 节点内走
PCIe 延迟低,跨节点就贵了。

> ⚠️ **这与 §3.6 的结论方向相反,但两者都对** —— §3.6 测的是**冷 prefill**
> (激活张量很大,TP 的 all-reduce 载荷重,所以减 TP 有利);这一节测的是**解码**
> (batch 极小,all-reduce 载荷只有百 KB 级,PP 的串行化反成主要成本)。
> **真实流量 86.2% 命中、是解码主导的(§7.2.1、§3.4.3),所以拓扑应按解码选。**

#### 1M 上的验证与现网切换 `[已生效]`

§3.10 测过「KV 池小 20% 时命中率完全相同(79.5% vs 79.4%)」,所以对命中率无影响。
唯一要留意的是 §3.4.3 那个场景:混合形状高并发时活跃上下文超过池容量会掉命中率,
门槛提前 20%。按真实流量平均 prompt 约 30k 算(2.89M ÷ 30k ≈ 96 个会话),够用。

#### 剩下的:这个负载下的 141 tok/s,九个配置都没撼动

> 能到 513.8 tok/s。141 是「30k 文档 + 每轮追加 2k」这个形状下 prefill 与 decode
> 争抢 2048 batch 预算的结果。

即使最优的 TP4×PP2,TPOT 仍是 8.9 → 57.7ms(并发 1 → 16),聚合输出封顶约
141 tok/s。**每副本可竞争并发从 1 提到约 1.5,没改变量级**(§3.4.2 的竞争力分析)。
这 20~33% 该拿(改参数就有)。**但"与百度差 5 倍"这个说法要按 §3.6.4 修正** ——

### 3.6.4 瓶颈定位:那个「解码天花板」根本不存在 `[实测 2026-09-16]`

§3.4.1 和 §3.6.2 都写了「解码几乎没有批处理收益、聚合封顶 141 tok/s」。
**两条都错**,而且错法不同。用引擎自带的计数器(`/metrics` 里已有,不用改代码)
加纯解码负载(500 token 进、1024 出,`ignore_eos`)重测,生产同配置
(1M / 批2048 / TP4×PP2):

| conc | 迭代/s | **step 耗时** | tok/迭代 | **生成 tok/s** | 投机接受率 |
|---|---|---|---|---|---|
| 1 | 38.0 | **26.3ms** | 5.1 | 123.1 | 45.1% |
| 4 | 38.6 | **25.9ms** | 9.9 | 244.5 | 45.7% |
| 16 | 20.6 | 48.6ms | 39.0 | **513.8** | 48.0% |

#### 错误一:指标选错了 —— TPOT 涨不等于批处理失效

**conc 1→4:step 耗时完全没变(26.3 → 25.9ms),吞吐翻倍(123 → 244 tok/s)。
批处理是完美的。** TPOT 从 7.8 涨到 15.4ms 只是「固定的 step 速率被两个流分摊」,
这是**正确行为**。

我之前拿 TPOT 当批处理效率的判据,得出「零收益」—— **TPOT 是结果不是原因**。
判据必须是 step 耗时(= 迭代速率的倒数)。真正开始变差是 4→16:
step 耗时 25.9 → 48.6ms,那才是进入受限区。

#### 错误二:141 tok/s 是 prefill 抢 batch 预算,不是解码上限

纯解码负载下 conc=16 能到 **513.8 tok/s**,是 §3.4.2 记录的 141 的 **3.6 倍**。

差别在负载形状:§3.4.2 用「30k 文档 + 每轮追加约 2k」,那 2k 的 prefill 和 decode
**抢同一个 `--max-num-batched-tokens 2048` 预算**。所以那个数是两者竞争的结果。

**这也把「与百度差 5 倍」的说法修正了** —— 百度 8 并发时每流 126 tok/s(聚合约
1,010),我们纯解码 16 并发是 514。差距是 2~4 倍且**取决于负载形状**,不是固定的 5 倍。

#### 真正的三个限制因素

**1. PP2 让每次迭代只能调度 41% 的并发请求**

投机解码下每个请求占 1+5 = 6 个 token 位置,所以:

```
conc=4:   9.9 tok/迭代 ÷ 6 = 1.6 个请求  → 占并发的 41%
conc=16: 39.0 tok/迭代 ÷ 6 = 6.5 个请求  → 占并发的 41%
```

**这是流水线的固有代价**:batch 被切成 micro-batch 分到两级,任一时刻只有约一半在
某一级。这独立地解释了 §3.6.2 为什么 TP4×PP2 打赢 TP2×PP4 —— PP4 会把这个比例
压到约 25%。

**2. conc 4→16 之间 step 耗时翻倍**,进入算力或访存受限区(具体是哪个见下)。

**3. 投机接受率只有 45~48%** —— dspark 草稿 5 个只中约 2.3 个,一半以上的草稿算力
白烧。这个数直接乘在 TPOT 上。

> ⚠️ **接受率这个数被我的测法压低了,而且影响今天所有 TPOT 数字。**
> 我的 prompt 是随机中文词拼的(见各节的 `WORDS` 语料),**草稿模型无法预测随机串**,
> 真实文本的接受率会高得多。所以**本文档所有 TPOT / 解码速率对真实流量都偏悲观**。
> 要拿准数必须用线上真实语料重测 —— 已列入 §10。

#### 瓶颈是每 step 约 20ms 的固定开销,不是带宽也不是算力

MFU 仪表答不了这个问题,原因很具体:`get_read_bytes_breakdown()`
(`vllm/v1/metrics/perf.py:470`)**只统计注意力层**的 `qkv_input/weight`、
`attn_input`、`out_input/weight`,**完全不含 MoE 权重**;而 FLOPs 估计器对
`deepseek_v4` 没注册,加了 `--enable-mfu-metrics` 后仍恒为 0。
实测读取只有 4.7~19.5 GB/s 且**随并发下降**(权重读取量随迭代数走,除以更长的
墙钟就更小)—— 这个数是注意力流量,而本模型是 MLA、`num_key_value_heads=1`,
KV 极小。**引用这个计数器判 MoE 的访存瓶颈会得出完全错误的结论。**

改用第一性原理算(256 专家 top-6,专家权重 TP4 切分后每个 3.34 MB,每卡 21.5 层,
投机解码下每请求占 6 个 token 位置):

| conc | token/step | 去重后专家数 | 每 step 读取 | 带宽利用 | 纯带宽该用 | **实测 step** | **非搬运部分** |
|---|---|---|---|---|---|---|---|
| 1 | 6 | 34 / 256 | 2.42 GB | **6%** | ~2.0ms | 26.3ms | **24.3ms(92%)** |
| 4 | 24 | 110 / 256 | 7.93 GB | **20%** | ~6.6ms | 25.9ms | **19.3ms(75%)** |
| 16 | 96 | 229 / 256 | 16.47 GB | **22%** | ~13.7ms | 48.6ms | **34.9ms(72%)** |

A100-40G 的 HBM 峰值 1,555 GB/s,实际可达 70~80%。**我们只用到 22%,离带宽瓶颈
差三倍以上。**

**每个 PP 边界的成本可以从已有数据反解**:§3.6.2 在 400k / conc=4 上测到
TP2×PP4 的 TPOT 是 33.6ms、TP4×PP2 是 23.1ms,比值 1.455。设
`step = F + n·X`(n = PP 边界数,PP2 为 1、PP4 为 3):

```
(F + 3X) / (F + X) = 1.455   →   X = 0.294 F
代入 PP2 实测 step 26.3ms:    F ≈ 20.3 ms     X ≈ 6.0 ms
                              F 摊到 43 层 = 0.47 ms/层
```

**所以一个解码 step 的 26.3ms 里:约 2ms 是搬权重、约 6ms 是一次 PP 跨界、
剩下约 20ms 说不清去处。** 这 20ms 就是与百度差 2~4 倍的所在 —— 不是硬件不行。

**两个嫌疑已排除:**

- **Sinkhorn 路由**(`hc_sinkhorn_iters: 20`):看着像每层 20 次迭代很贵,但
  `num_hash_layers: 3` —— `hc_*` 只作用于 3 层而非 43 层,量级不够。
- **稀疏注意力 indexer**(`index_topk: 512`,`index_n_heads: 64`):§3.9.1 实测
  TPOT 从 8k 到 1M 一直是 10~13ms,**对上下文长度不敏感**,所以不是它。

#### 结案:瓶颈是上千个微型 MoE GEMM 的占用率 `[实测]`

不用 `nsys` 也能定到这一层 —— 做 **eager 与 CUDA graph 的相减**。同配置起两个实例,
只差 `--enforce-eager`:

| conc | CUDA graph step | eager step | graph 快 |
|---|---|---|---|
| 1 | **27.3ms** | **212.8ms** | 7.8 倍 |
| 4 | 27.5ms | 181.9ms | 6.6 倍 |
| 16 | 56.4ms | 182.4ms | 3.2 倍 |

**CUDA graph 是生效的,而且消掉了约 185ms 的 launch/dispatch 开销。** 所以 graph
模式下剩的时间是 **GPU 真的在执行 kernel**,不是调度开销。

旁证:**eager 的 step 耗时在 conc 4→16 之间完全不变**(181.9 → 182.4ms),而 graph
模式从 27.5 涨到 56.4 —— eager 被固定开销淹没,graph 模式才露出真实工作量。

**把 graph 模式的 step 拆开**(PP 跨界取上面反解的 6.0ms,搬权重按 1.2 TB/s 有效带宽):

| conc | step | 搬权重 | PP 跨界 | **kernel 执行** | 去重后专家数 |
|---|---|---|---|---|---|
| 1 | 27.3ms | 2.0ms | 6.0ms | **19.2ms** | 34 |
| 4 | 27.5ms | 6.6ms | 6.0ms | **14.9ms** | 110 |
| 16 | 56.4ms | 13.7ms | 6.0ms | **36.7ms** | 229 |

**决定性的数字:专家数 34 → 229(工作量 6.7 倍),kernel 执行只涨 1.91 倍。**

这是**占用率受限**的教科书特征。每个专家 GEMM 的形状是 `6 token × 4096 × 2048`
(conc=1),极小,张量核喂不饱;batch 变大后 GEMM 变大、效率随之提升。conc=1 时
最极端:19.2ms 的 kernel 时间只搬 2.42 GB,带宽利用 6%。

**这解释了今天所有「为什么没效果」:**

| 现象 | 解释 |
|---|---|
| 九个配置都撼不动(§3.6.2) | 批预算、上下文长度、EP、投机解码**都不改变 GEMM 的形状** |
| `marlin` 只有 4~8%(§3.6.3) | 更好的内核,但仍是同样的微型 GEMM 结构 |
| TP4×PP2 有效 +18~33% | 它减少的是 **PP 跨界次数**(每次 6ms),不是 GEMM 效率 |
| 与供应商差 2~4 倍 | 真正的修法是**专家分组 GEMM**(`deep_gemm_mega_moe`、`flashinfer_moe_ep_mega_*`),而 §3.6.3 的白名单实测显示**它们全部要 sm90+** |

#### 由此得到一个无法靠调参绕开的张力

```
conc=1:  聚合 123 tok/s,TPOT  8.2ms   →  GPU 占用率 6%,硬件基本闲着
conc=16: 聚合 514 tok/s,TPOT 31.4ms   →  吞吐 4.2 倍,TPOT 3.8 倍
```

- 按**延迟**选运行点(低并发,§3.6.4 的竞争力分析)→ 硬件严重闲置
- 按**效率**选运行点(高并发)→ 单流 TPOT 变差近 4 倍

**这是 sm80 上 MoE 解码的结构性约束,不是配置问题。** 出路只有三条:
换 sm90+ 拿到分组 GEMM 内核、减少专家数(剪枝,§5.1 的 REAP 系)、
或者明确接受「高并发 + 稍差的单流延迟」这个运行点并按它定价。

> `nsys` / `ncu` 镜像里都没有。但上面这套 eager-vs-graph 相减 + 第一性原理的
> 带宽估算,已经把瓶颈定到「kernel 执行 + 占用率」这一层,**不装 profiler 也够用**。
> 真要拆到单个 kernel 才需要装。

#### 方法论:为什么绕了一整天

`/metrics` 里这几个计数器**一开始就有**,不用改代码、不用重启:

```
vllm:iteration_tokens_total_{count,sum}          ← step 耗时与每步 batch,判批处理
vllm:generation_tokens_total                      ← 真实聚合吞吐
vllm:spec_decode_num_{accepted,draft}_tokens_total ← 接受率
vllm:estimated_{flops,read_bytes}_per_gpu_total    ← 需 --enable-mfu-metrics 才计算
```

### 3.9.1 上下文长度扫描:延迟曲线 `[实测 2026-09-15]`

上面那张表回答的是「取不取得出来」,这一张回答「等多久」。直连实例口
`10.0.0.216:40045`,`conc=1`(隔离单请求成本),`out=128`、`ignore_eos=true`,
prompt 长度用 `/tokenize` 校准过(实测 **1.7391 字符/token**,直接按 2.0 估会差 15%,
逼近 1M 时这个误差是致命的)。

| 上下文 | TTFT p50 | prefill 吞吐 | TPOT p50 | 单请求墙钟 |
|---|---|---|---|---|
| 8k | 0.92s | 8,700 tok/s | 10.7ms | 2.2s |
| 32k | 2.59s | **12,350 tok/s** ← 峰值 | 10.4ms | 3.9s |
| 128k | 10.86s | 11,800 tok/s | 12.4ms | 16.9s |
| 256k | 25.72s | 9,950 tok/s | 11.4ms | 27.4s |
| 512k | 69.06s | 7,410 tok/s | 11.3ms | 71.2s |
| **1M** | **200.03s** | 5,000 tok/s | 13.2ms | 202.5s |

两条结论,方向相反:

1. **TPOT 从 8k 到 1M 一直是 10~13ms,完全不受上下文长度影响。** 解码在长上下文下
   不退化 —— 这和 §2.1 的「热路径全程碾压」是同一件事的另一面。
2. **prefill 在 32k 见顶后一路衰减**(12,350 → 5,000 tok/s,注意力的二次项),
   TTFT 从 8k 到 1M 涨了 **217 倍**(上下文只涨 128 倍),略微超线性。

**产品含义:1M 技术上通,但 200 秒的首字延迟卖不成交互功能。**
按「首字可接受」倒推可用上限:

| 首字预算 | 可用上下文 |
|---|---|
| ≤ 3s | ~32k |
| ≤ 11s | ~128k |
| ≤ 26s | ~256k |
| ≤ 70s | ~512k |
| 200s | 1M(只能当异步/批处理功能) |

**但这个结论被前缀缓存整个改写了**:1M 文档只在首轮付这 200 秒,之后每轮都是
命中态的 1~2 秒(§3.7 已验证 1M 多轮累积)。所以真实 UX 是「第一次等 3 分钟,
之后每次 2 秒」。**这让 §7.3 第 3 层的预热从「延迟优化」变成了「让 1M 可用的
前提条件」** —— 对 1M 文档,预热是把 200 秒挪进用户读文档的时间里,不是省几秒。
这比 §7.3 里按 8.4% 请求算出来的那笔账重要得多。

> ⚠️ 测这个时不要照抄 §3.9 的 `max_tokens=64`。那一节明确写了左列的「断崖」是输出
> 预算造成的假象。我自己写探针时就差点又踩一次。

#### 1M 与供应商的正面对比:差距全在冷首轮 `[实测 2026-09-16]`

950k 首轮 + 一轮续写(追加约 800 token),同一套回放经网关打三家:

| | 轮0 TTFT(冷) | prefill 吞吐 | 轮1 TTFT(热) | 轮1 命中 |
|---|---|---|---|---|
| **我们** | **185.5s** | 5,122 tok/s | **7.8s** ← 最快 | 99.9% |
| 火山 | **61.4s** | **15,477 tok/s** | 9.0s | 99.9% |
| 并行 | 61.9s | 15,352 tok/s | 8.2s | 99.9% |

**三家都能处理 1M,三家都把 1M 前缀缓存住了(全是 99.9%)。** 原以为供应商在这种
体量上可能留不住缓存 —— **不成立**。所以缓存能力不是差异化。

**差异全部集中在冷首轮:它们快 3 倍。热续写我们反而最快。** 它们的 prefill 也随
长度衰减(火山 300k 时 21,700 → 1M 时 15,477;我们 9,400 → 5,122),衰减比例
接近(0.71 / 0.54),是绝对值差 3 倍。

**由此「1M 要不要自己做」成为一笔可算的账**(单价取自现网计费:输入 ¥3/M、
缓存输入 ¥0.1/M;供应商价取 §2.3 反推的纯输入 ¥0.861/M):

```
一个 950k 冷首轮:   我们收 ¥2.85    外购成本 ¥0.82   →  外购毛利 ¥2.03(71%)
                     自己做占用 185s × 8 卡 = 0.41 GPU·小时
之后每轮热续写:     我们收 ¥0.095(缓存价),几乎不耗算力  →  近乎纯毛利
```

**缺的输入是我们自己的 GPU 单位成本。** 若折算 ¥5/卡·小时,自己做冷首轮约 ¥2.06,
**比外购的 ¥0.82 贵** —— 8 张卡被一个请求占 3 分钟。三个现实选项:

| 方案 | 毛利 | 代价 |
|---|---|---|
| 冷首轮外购、整个会话留在供应商 | 71% | 把后面近乎纯毛利的续写也让出去 |
| **全自己做 + 预热(§7.3)** | **全部保留** | 0.41 GPU·小时,且需「文档先到、问题后到」 |
| 按机队负载动态选:空闲自己做、打满外购 | 介于两者 | 网关要有负载感知(与 §3.4.5 的准入控制同一套) |

**「冷首轮外购、续写自己做」做不到** —— 那要求把 KV 从供应商搬回来。
所以第 2 个是长期正确的,第 3 个是它的稳健版。

## 3.10 GPU KV 池的真实作用:是并发天花板,不是命中率 `[实测 2026-09-15]`

开了 `--kv-offloading-size` 之后,KV 变成两层:GPU 是一级,宿主内存是二级。
两层的容量关系要按**全局**口径算,别按每节点:

```
一级(GPU)   = 8 卡 × 11.46 GiB = 91.7 GiB 全局
二级(宿主)  = cpu_bytes_to_use = 75 GiB 全局
              每节点 mmap 一份 80.53 GB 的 region(sparse),
              但每个 rank 只 pin 自己的 1/8 切片:10.06 GB × 8 = 80.5 GB = 75 GiB
              每节点实际 pin = 4 个本地 rank × 10.06 = 40.24 GB
```

**所以二级是一级的 0.82 倍,略小,不是更大。** 曾误算成「每节点 75 GiB × 2 节点
= 150 GiB、比一级大 1.6 倍」—— 那是把全局量当成了每节点量。

§3.6.1 的三臂给出了直接证据 —— **KV 池差 20%,命中率完全相同**:

| 臂 | GPU KV 池 | 1M 并发 | 真实形状命中率 |
|---|---|---|---|
| D | 3,611,775 | 3.44× | **79.4%** |
| C | 2,890,000(**−20%**) | 2.76× | **79.5%** |
| E | 2,126,396(**−41%**) | 2.03× | (合成臂,未跑形状) |

配合 §3.1 的淘汰重入实测(GPU 热态 **2.70s** vs 被挤出后重入 **2.79s**,只差 3%,
比重算的 106.34s 快 38 倍),结论是:

> **被挤出 GPU 的前缀不会丢,落到宿主内存那层,命中照样算命中。
> 所以 GPU KV 池的大小不决定命中率。**

那它决定什么?**高并发时的人均上下文上限。** 每个在跑的请求,上下文里每个 token
的 KV 都要驻留到请求结束:

```
3,611,775 ÷ max_num_seqs(32) = 每条请求平均 112,868 token
```

**32 并发时人均上下文超过约 11.3 万就开始抢占。** 对照 §1.2 的线上分布:

| | prompt tokens | 32 并发时 |
|---|---|---|
| 中位 | 39,543 | 安全(用 35%) |
| **P75** | **271,849** | **超 2.4 倍** |
| P90 | 490,194 | 超 4.3 倍 |

§3.6.1 那几轮(8 会话 × 19 万 = 1.59M,占池子 44%)**抢占次数全部为 0**,
说明当前并发水平下这个天花板还没碰到。

**评估「用 KV 容量换别的东西」这类选项时,不要按 KV token 数的降幅算损失。**
要看两件事:二级缓存是否装得下被挤出的部分(现在余量充足),以及并发是否高到
让容量真正成为约束(§3.3:8 会话下 100/150 GiB 无差别,24 会话才差 13.9%)。
C 臂输掉 22.1% 与它少 20% 的 KV 池**无关** —— 它输在冷 prefill(轮0 TTFT
119.3s vs 69.7s)。

### 4.1 Triton JIT 缓存**不能**放共享 NFS `[实测]`

`docker/run_multinode_sm80.sh` 默认把 `/root/.cache` 与 `/root/.triton`
挂到 `/nfs-models/vllm-backport-cache*`,本意是「一台热身完其余节点直接复用」。
**多实例并发下这会把引擎打死**,而且它在两个维度上都更差。

5 个 TP2×PP4 实例(40 个 rank 进程)并发压测时,其中 **2 个**在第一轮就挂:

```
OSError: [Errno 116] Stale file handle
  在 deepseek_v4/.../combine_topk_swa_indices 的 Triton kernel 启动处
→ EngineCore 挂掉 → 之后所有请求 HTTP 500
```

ESTALE 是 NFS 的错误码。缓存规模决定了这是个元数据密集负载,不是带宽负载 ——
**1.9 GB / 40,080 个文件**。实测各介质(2000 个 50 KB 文件,写用临时文件 + rename,
与 Triton 的落盘方式一致):

| 介质 | 写 | 读 |
|---|---|---|
| **本地盘** | 2.9s(**690 文件/s**) | **1.0s** |
| NFS | 24.8s(81 文件/s)**慢 8.5×** | 10.2s **慢 10×** |
| tmpfs | 2.6s(769 文件/s) | 1.0s |

也就是说共享 NFS 缓存既会打死引擎,读 4 万个文件还慢 10 倍
(本地约 40s vs NFS 约 200s)——「一台热身完其余复用」实际上在**拖慢**启动。

**结论:用本地盘。** `CACHE_HOST_DIR=/var/cache/vllm-backport`。
空间不是问题(需要 1.9 GB,节点本地盘空闲 673 GB)。

顺带否掉「NFS 只读种子 + 本地写」这个折中:`cp -r` 那 1.9 GB / 4 万文件
实测 **191s**,比本地重新 JIT 还贵。

> 机队规模上这是硬约束:35 个实例 × 8 rank = 280 个进程共写一份 NFS 缓存。

## 5. 经济性敏感模型

标定(从 r=8.09、b=32、零复用的 421.8 tokens/s/卡 与 prefill 占 30% 反推):

```
纯 prefill 速率 p = 1,251 tokens/s/卡
纯 decode  速率 d =    66.3 tokens/s/卡      (差 19 倍)
T(r) = (r+1) / (r/p + 1/d)
混合单价 P(r) = (1.35r + 4.05)/(r+1)
```

独立校验:r=4 预测 273 / 实测 222 → **模型偏乐观 23%**,输出重的一侧真实更差。

| 入:出 | 混合单价 | 盈亏平衡 | 可达(b=32 零复用) | 毛利 |
|---|---|---|---|---|
| 1:1 | 2.700 | 206 | 126 | −64% |
| 2:1 | 2.250 | 247 | 180 | −37% |
| 4:1 | 1.890 | 294 | 273 | −7.5% |
| **4.8:1** | 1.816 | 306 | 306 | **0%** |
| 8:1 | 1.650 | 337 | 419 | +20% |
| 16:1 | 1.509 | 368 | 610 | +40% |
| 32:1 | 1.432 | 388 | 812 | +52% |

**真正的盈亏平衡不是「337 tokens/s/卡」,是「输入:输出 ≥ 4.8:1」。** 真实流量算力比 22.8:1,远在安全区。

> 需求文档里的 **680 tokens/s/卡是作者自选的 50% 毛利档位**(`HANDOFF:544`),不是用户需求;且它从 1125 下调而来(`HANDOFF:548`)。**不应作为目标对待** —— 毛利是结果,不是输入。

## 5.1 换权重:量化候选的全量调研 `[元数据实测 2026-09-16]`

§3.6.2 的结论是调参已到顶(拓扑 +20~33%,MoE 后端再 +4~8%)。当时以为剩下的瓶颈
是 MoE 的 decode 内核,于是调研了换权重格式这条路 —— **后来 §3.6.4 定位出瓶颈不在
那里**,但这份调研的判据(格式白名单、DSpark 字段、专家数)仍然有用,而且它本身
得出了一个干净的否定结论。理由原本是硬件级的:

```
A100 (sm80) 没有 FP8 张量核,也没有 MXFP4 原生内核 → 权重必须反量化成 BF16 再算
A100 有原生 INT8 张量核(624 TOPS,是 BF16 的 2 倍)
A100 上 INT4 group-wise 有一流的 Marlin 内核,group=128 是它的最优 group size
```

我们当前权重:**MoE 专家 MXFP4(约 4 bit)+ 线性层 FP8**,合计 166.9 GB
(`config.json` 写 `quant_method: fp8`,但报错信息 `Mxfp4 MoE backend` 才是 MoE 的
真实路径)。

### INT8 w8a8:8 卡上物理装不下,不是"不划算"

```
8 × A100-40G 可用显存  ≈ 316 GB
INT8 权重                312.3 GB
剩给 KV + 激活 + CUDA graph:  不到 4 GB     →  起不来
```

16 卡(4 节点)一个副本能装下,而且**每卡权重字节数几乎不变**(19.5 GB 对现在
20.9 GB),所以解码不会变慢、prefill 能吃到原生 INT8 的 2 倍算力。但代价两条:
**副本数腰斩**(每副本 2 节点 → 4 节点),以及 **PP 被迫 4 级**——§3.6.2 刚实测
PP4 比 PP2 的解码差 28~33%,会吃掉一部分收益。净收益是正还是负,得实测。**暂缓。**

## 6. 推荐配置

```bash
--tensor-parallel-size 4 --pipeline-parallel-size 2   # ★ 2026-09-16 改:按解码选,见 §3.6.2
                                 # §3.6 按冷 prefill 选的是 TP2×PP4,方向相反但两者都对;
                                 # 真实流量 86.2% 命中、解码主导,所以按解码选
--max-model-len 1048576          # 覆盖 99.7% 请求 / 98.3% 计费量
--max-num-batched-tokens 2048    # ★ 1M 的硬约束;实测 2048/4096/8192 对解码无差别(§3.6.2)
--max-num-seqs 32                # 实测最优;64 反而 −31%(TP4×PP2 下测)
--gpu-memory-utilization 0.85    # 0.90 会 OOM
--block-size 256
--kv-cache-dtype fp8
--enable-prefix-caching
--kv-offloading-size 150 --kv-offloading-backend native   # ★ TP4×PP2 用 150!改拓扑最易漏
                                 # 该值不按 PP 摊分:每节点用量 = (PP/节点数) × 本值。
                                 # TP4×PP2 用 150,TP2×PP4 必须减半到 75,否则
                                 # cudaHostRegister 失败。>125 GiB 另需 memfd 后端。
--enable-expert-parallel         # 保持开:我们 +17.2%(外部仓在 TP=8 下相反,见 §3.8)
--speculative-config '{"method":"dspark","num_speculative_tokens":5,"draft_sample_method":"greedy"}'
--kernel-config '{"moe_backend":"marlin"}'   # ★ 可选,TPOT +4~8%(§3.6.3)
--tokenizer-mode deepseek_v4 --tool-call-parser deepseek_v4 --reasoning-parser deepseek_v4
--enable-auto-tool-choice --chat-template-content-format string
# 不要传 --enforce-eager;不要传 --default-chat-template-kwargs(死配置)

环境变量:
VLLM_DETERMINISTIC_MOE_ALIGN=0                 # +9%
VLLM_KV_OFFLOAD_REGION_BACKEND=memfd           # 卸载 >125 GiB 时必需
VLLM_REASONING_OUTPUT_AS_REASONING_CONTENT=1   # 无感知切换必需,见 §2.2
NCCL_IB_GID_INDEX=3  NCCL_ALGO=Ring  NCCL_PROTO=Simple
# NCCL_IB_HCA 不必再裁成 mlx5_0,mlx5_2 —— 4 轨都是线速(§7.4.1)
# 不要设 VLLM_PP_LAYER_PARTITION(真实形状下变慢)
```

> ⚠️ **2026-09-16 前这份代码块与下面的注解自相矛盾**:代码块写 `524288 + 8192`,
> 注解说「默认建议 1M」(而 1M 必须配 2048),照代码块抄会得到第三种配置。
> 已按现网实际运行的配置对齐,并把拓扑改成 TP4×PP2(§3.6.2)。
>
> **`--max-model-len` 填 524288 还是 1048576?**
> 1M 已实测可用(§3.7:50 轮累积到 1,006,903,针召回 100%),所以**能填 1M**,
> 而且填了就不必在网关做长度分流(1M 覆盖 99.7% 请求 / 98.3% 计费量)。
> 代价:批预算**必须**降到 2048(§3.7 那组就是 `max-model-len 1048576` + 批 2048)。
> 这是硬约束不是偏好 —— 1M + 批 8192 启动就失败(需 5.07 GiB KV > 可用 5.06 GiB),
> 4096 能起但吃掉 41% 的 KV 池且 −1.7%(§3.6.1)。
> 而这个代价比原先以为的更小:批预算 8192→2048 不仅只影响冷 prefill 2~5%(§4),
> 对**并发 decode 也没有影响**(400K 下 8192 与 2048 分别是 40.8 / 41.2 每卡,§3.6.1)。
> 贵的是 `max-model-len` 本身:400K→1M 在批 8192 下要多花 5.57 GiB/卡,
> 因为 sparse indexer 元数据与 CUDA graph 地址空间都随它线性增长。
> 512K 的唯一理由是「只想覆盖 90.9% 请求 / 62.3% 计费量、把长尾推给供应商」。
> **默认建议 1M**,除非明确要做长度分流。

> **上面这份配置不需要改引擎源码**,只是启动参数与环境变量。
>
> 但本轮调优确实产生了两个引擎改动,都与上面的配置无关(默认不生效):
>
> | commit | 内容 | 上线是否需要 |

> | `f1c429fd8` | `VLLM_REASONING_OUTPUT_AS_REASONING_CONTENT`:思维链按 `reasoning_content` 输出 | **需要**(无感知切换,见 §2.2) |
> | `9a53df78b` | 修 `VLLM_UNREPLICATE_ATTN_GEMMS` 会崩引擎的 bug | 不需要(该开关已否,见 §4) |

### 6.1 在 GPUStack 上怎么填这些参数 `[已核对源码]`

GPUStack 托管的实例不走 `docker/run_multinode_sm80.sh`,参数填在**模型的两个字段**里。

**① 后端参数 → 模型的 `backend_parameters`(UI 里"后端参数"那一栏)**

填法就是把上面那串命令行参数**逐个 token** 填进去,GPUStack 会自己规范化成
`--k=v`(`utils/command.py:170 format_backend_parameters`):

```
--tensor-parallel-size=2
--pipeline-parallel-size=4
--max-model-len=524288
--max-num-batched-tokens=8192
--max-num-seqs=32
--gpu-memory-utilization=0.85
--block-size=256
--kv-cache-dtype=fp8
--enable-prefix-caching
--kv-offloading-size=75
--kv-offloading-backend=native
--enable-expert-parallel
--speculative-config={"method":"dspark","num_speculative_tokens":5,"draft_sample_method":"greedy"}
--tokenizer-mode=deepseek_v4
--reasoning-parser=deepseek_v4
--tool-call-parser=deepseek_v4
--enable-auto-tool-choice
--chat-template-content-format=string
--enable-prompt-tokens-details
--trust-remote-code
--disable-custom-all-reduce
```

**TP/PP 必须自己填。** GPUStack 会按显存自己算一组
(`worker/backends/base.py:1270 cal_distributed_parallelism_arguments`),但注入时走
`extend_args_no_exist`(`utils/command.py:137`)—— **只在用户没填时才补**,所以我们填了
就以我们的为准。不填的话它大概率给出 TP4×PP2,而那比 TP2×PP4 慢 51.6%(§3.6)。

**`--enable-prompt-tokens-details` 必须显式加。** 它默认关
(`cli_args.py:132`),不开的话 `usage.prompt_tokens_details.cached_tokens` 恒为空,
new-api 会把全部 prompt 按 ¥3.00 计价 —— **客户账单高 3.81 倍**(§1.1)。

**② 环境变量 → 模型的 `env`(UI 里"环境变量")**

```
VLLM_DETERMINISTIC_MOE_ALIGN=0
VLLM_KV_OFFLOAD_REGION_BACKEND=memfd
VLLM_REASONING_OUTPUT_AS_REASONING_CONTENT=1
NCCL_IB_GID_INDEX=3
NCCL_ALGO=Ring
NCCL_PROTO=Simple
```

注入点在 `worker/backends/base.py:540`(`env.update(self._model.env)`),会覆盖
worker 自身继承的同名变量。

**`NCCL_IB_HCA` 可以不填。** 55 台 × 4 轨 RDMA 都是线速(§7.4.1),不需要像原来那样
裁成 `mlx5_0,mlx5_2`。唯一的例外是 §7.4.2 那种单轨故障未修复的机器,那时按坏轨裁剪。

**不要填的**:`--enforce-eager`(会关掉 CUDA graph)、`VLLM_PP_LAYER_PARTITION`
(真实形状下变慢,§0)、`--default-chat-template-kwargs`(死配置,`tokenizer_config.json`
里零匹配)。

**③ JIT 缓存不用管**

§4.1 说的「Triton 缓存不能放共享 NFS」**不适用于 GPUStack 托管的实例**:它把
`VLLM_CACHE_ROOT` 指向 `<data_dir>/cache/vllm`(`worker/backends/vllm.py:416`),而
worker 的 data_dir 是 `/var/lib/gpustack` → docker volume → **本地盘**。那个 ESTALE
问题只出在我自己那个把 `/root/.cache` 挂到 NFS 的多节点脚本上。

> 只有一处值得显式设:`VLLM_CACHE_ROOT` 管的是 vLLM 自己的缓存,Triton 的 JIT 缓存
> 是否也落在同一路径取决于版本。若在日志里看到 `Stale file handle`,就在 `env` 里加
> `TRITON_CACHE_DIR=/var/lib/gpustack/cache/triton` 显式钉到本地盘。

**④ 一个实例 = 2 个节点 × 4 卡**

TP2 × PP4 = 8 卡。GPUStack 的调度器按 `computed_resource_claim` 分配,确认它把
8 张卡分在**两台**机器上(每台 4 张),而不是别的切法。

## 7. 网关设计(机队层面,比任何单实例调参都重要)

### 7.1 分流键不能用「总上下文长度」

我们的耗时由**未命中的新增 token** 决定,不由总长度决定:

- 490k 上下文、489k 已缓存 → **2.42s**(供应商 5.52s,我们快 2.3×)
- 250k 上下文、全是新的 → **~53s**(供应商 ~6s,我们慢 9×)

后者短一半却慢 22 倍。按总长度分流会把「长但全热」(我们最赚)推给供应商,把「短但全冷」(我们最亏)留给自己。

### 7.2 应该按会话分流

1. **会话首轮**按 prompt 大小决定去向(超大文档首轮 → 供应商)
2. 一旦落到我们这边,**该会话后续所有轮次锁定同一实例**,不管上下文涨多大
3. 配合预热(§7.3),首轮也能抢回来

### 7.2.1 会话亲和已上线:命中率 34.1% → 78.4% `[实测 2026-09-15]`

第 2 条已实现并验证。做法是 **new-api 直连实例**,不是给网关下发路由头 ——
后者试过,方向是反的,详见下面。

**结果**(8 会话 × 5 轮,文档按 §1.2 分位点采样,4 副本):

| | 整体命中率 | 轮0 | 轮1 | 轮2 | 轮3 | 轮4 |
|---|---|---|---|---|---|---|
| 亲和未生效(4 副本随机分流) | **34.1%** | 0% | 0% | 38% | 62% | 75% |
| 亲和未生效(3 副本,候选少所以偏高) | 48.5% | 0% | 12% | 62% | 100% | 75% |
| **亲和生效(直连)** | **78.4%** | 0% | **100%** | **100%** | **100%** | **100%** |

「整体命中率」是全部请求的 token 加权前缀命中率;轮0~轮4 那几列是**命中轮次占比**
(该轮的 8 个会话里有几个命中)。生效后轮1 起每个会话的每一轮都
精确落回同一实例,**轮内命中率 96.6~97.0%** ——剩下 3% 是每轮新增的 token,本来
就该重算。延迟同步下降(轮1-4 中位 4.45/4.46/3.01/2.77s → 2.48/2.13/2.23/2.33s):
既不用重算前缀,又少一跳网关。

按 §1.1 的乘数关系,**每卡计费产能约 3 倍**(1/(1−0.341)=1.52 → 1/(1−0.784)=4.63)。

**判据必须用「命中轮次占比」,不能用累计命中率。** 同事那台线上实例的
`prefix_cache_hits_total / queries_total` 累计是 89.3%,但同一套受控回放打上去
只有 32.0% —— 累计值混了历史上副本数更少的时期和跨会话共享前缀的流量,判断
亲和是否生效时会骗人。

#### 为什么不能给网关下发路由头 `[实测否掉]`

`X-GPUStack-Model-Instance` 看起来正是为此而设(网关的 `set-model-pre-route`
插件配置里写着 `clusterNameHeader: X-GPUStack-Model-Instance`),而 gpustack 的
`transformer` 插件又在剥离它。于是很自然地推断「剥离是多余的,去掉就能钉实例」。
**方向整个是反的**:那个头是「网关 → worker」的输出,不是「客户端 → 网关」的输入。

1. **架构上它必须是输出。** 所有 worker 都是 `proxy_mode=worker`,于是
   `model_instance_registry`(`gateway/utils.py:261`)走
   `_worker_reserve_proxy_registry` —— **每个实例的 service 名不同,但地址全是
   同一个 `worker_ip:10150`**。网关选完 cluster 后 worker 无法从地址分辨该转给
   哪个实例,只能靠网关把选择结果写进这个头告诉它,再由
   `routes/worker/proxy.py` 的 `set_port_from_model_name` 转到真实端口。
2. **网关的 `weighted_clusters` 选择不读任何客户端头。** 实测:发
   `model-57-1426` 的请求落到了别的 worker,worker 查不到本机有这个实例就 404。
3. **改不了那个插件。** `set-model-pre-route` 是 pip 包
   `gpustack_higress_plugins` 里的预编译 `plugin.wasm`,无源码。

放开剥离的实际后果:**6 次请求 3 次 404**(`No running model instance found for
model name: 1426`)。把一个静默的性能问题换成了显性的可用性故障 —— 原来的剥离
**正确且必要**,它保证插件写入的值是权威的、不被客户端的陈旧值抢先(`transformer`
里对 `x-gpustack-model` 的 `RETAIN_FIRST` dedupe 规则针对的是同一类问题)。
已回退(gpustack `aaf1dba5`)。

一致性哈希也不行:ring hash 在**单个 cluster 内部的 endpoints** 之间选,而这里
每个实例是独立 cluster,选择发生在 route 级的 `weighted_clusters` 上。

#### 直连的实现要点

```
new-api 取对话稳定前缀 → HRW 选实例 → 把目标 URL 改写成 worker_ip:port
```

- **不发那个头。** 直连时它没用(不经网关和 worker 代理),回退到网关时发了反而
  触发上面那个 404。new-api 还把它加进了客户端头透传的跳过列表:我们自己不发,
  也绝不接受客户端传入。
- **HRW 的盐用实例身份**(`model-<model_id>-<instance_id>`)**而不是地址**。用地址
  的话实例重启换端口会把它承接的那批会话全部重映射,缓存白丢。
- **盐改短会让 HRW 分布退化。** 从 `model-7-23.static` 改成 `model-7-23` 后,扩容
  一个实例的重映射比例从理论值 1/(N+1)≈11% 涨到 **24.7%**:FNV-1a 是乘-异或链、
  雪崩弱,而实例标识只在末尾几字节有差异,相邻实例分数高度相关。原来带 `.static`
  多出的 7 字节混淆轮数才让它勉强达标 —— 那是运气不是设计。加 splitmix64 终末
  混淆后回到正常。
- **必须回退到网关。** 直连绕过了 ingress 的 `proxy-next-upstream` 重试策略,所以
  连接层失败与 404/502/503/504 都要退回渠道原本的 Base URL 重试一次。404 必须在
  回退集合里:它是路径或实例不对的信号,而且落在外层
  `AutomaticRetryStatusCodeRanges`(401-407)内,不兜住就白烧一次换渠道重试。
- **渠道 Base URL 的路径前缀要去掉。** 实例端口上只有裸 `/v1/...`。
  `http://gw/gpustack` 那种渠道若只换 scheme+host,会打到
  `http://<ip>:<port>/gpustack/v1/...`,每个请求都 404。
- **发请求前做有界拨号探测(2 秒)。** 共享的 relay client 在 `RELAY_TIMEOUT=0`
  (默认)下既无 `Client.Timeout` 也无 `Transport.DialContext`,**黑洞**地址
  (丢包而非拒连)会把请求拖到操作系统的 TCP connect 超时,Linux 上约 130 秒。
- **直连失败要就地失效实例列表。** 回退成功后整个请求返回 200,relay 层按状态码
  触发的失效逻辑根本不会执行,死实例会在缓存里停留整个 30 秒 TTL 被反复选中。

#### 管理密钥的作用域:最难查的一种失败 `[一次两小时的排查]`

new-api 需要调 `/v2/model-instances` 拿实例列表。这个密钥的**作用域**必须能读到
模型与实例,否则:

```
HTTP 200,pagination.total = 0
```

**不是 401 也不是 403,就是空。** 因为该接口按
`owner_principal_id == current_principal_id` 过滤(`routes/models.py:146`),而
API key 认证时这个值恒等于**密钥自己的 owner**
(`api/tenant.py:256`,且 `X-Organization-Id` 对 API key 被忽略 —— 实测填 1/2/3
都是 0 条)。模型与实例归组织所有,个人作用域的密钥一条都匹配不上。

于是亲和按设计静默跳过(拉不到实例就不做),表现为命中率停在随机分流的水平,
两侧都不报错。同一个用户的两个密钥在 UI 上长得完全一样:

```
gpustack_6aaf***  owner_principal_id=3     → 0 条实例      ← 渠道里填的是这个
gpustack_0e98***  owner_principal_id=null  → 70 条实例
```

**正确的密钥:** 平台管理员在「无组织上下文」(All 模式)下创建的,
`owner_principal_id` 为 `NULL`,这样 `bypass_tenant_filter` 放行、可跨组织读
(`routes/api_keys.py:161-178` 的注释写明了这个设计);或者至少属于模型所在的组织。

两个配套改动:
- gpustack-ui 的密钥列表加了「作用域」列(`全部` / `个人` / 组织名),让这个
  隐形属性可见(commit `cd5cca25`)。
- new-api 对这条路径加了指名道姓的日志:**「实例列表为空。若管理 API 返回的是
  HTTP 200 + total=0,说明管理密钥的作用域不对」**。这个功能的失败形态全是静默的,
  日志的措辞必须直接把答案写出来,而不是只报现象。

### 7.2.2 重启 gpustack server 会拆掉运行中的模型实例 `[实测,一次事故]`

升级 server 时我判断「server 不在推理数据路径上,重启几秒无影响」。**错的。**

```
19:35:27  worker ERROR - Error watching models: All connection attempts failed   ← server 被重启
19:35:45  worker ERROR - cleanup_orphan_workloads 失败:
                         PID 175859 is zombie and can not be killed.
                         Use the --init option when creating containers ...
19:35:54  worker INFO  - Stopped model instance 86grr        ← 运行中的**从节点**被当成孤儿拆掉
19:35:55  worker INFO  - Started → "waits for main worker 10.0.0.11 to be initialized"
   ...(主节点毫无察觉地继续运行 15 分钟)...
19:50:03  主节点收到第一个请求 → PP isend_tensor_dict 到已死的对端
          RuntimeError: gloo ... Connection closed by peer [10.0.0.134]
          → EngineCore fatal → 主节点也死
19:50:30  worker INFO  - Restarting (attempt 1)
```

**机制:** server 一断,worker 的 `cleanup_orphan_workloads` 会把运行中的实例当成
孤儿拆除。PP 拓扑下**从节点被单独拆掉时主节点不会立刻发现** —— 它要等下一个请求
走到 `isend_tensor_dict` 才崩。所以「实例状态是 running」和「实例能服务」之间有个
最长十几分钟的盲区(同一盲区也解释了 `state=starting` 的实例为何仍被网关选中、
对外表现为 `Cannot connect to host <ip>:<port>`)。

**实测代价:** 一个副本从 19:35 被破坏、19:50 崩溃、加上约 10 分钟重载,共约
**40 分钟单副本不可用**;4 副本下表现为约 1/4 的请求可能失败。

**放大器:容器创建时没有 `--init`。** 僵尸进程让 `docker rm` 杀不掉,拆除失败后
重试,状态更乱。容器创建在 pip 包 `gpustack_runtime` 的
`deployer/docker.py::containers.create()` 里,**不传 `init`**,要修得改那个包。

**所以升级 server 要按滚动窗口做,或者明确接受会丢一个副本。**「只升 server 不升
worker」这个判断本身是对的(9 天的 delta 里 `schemas/` `client/` `api/` `worker/`
零改动,升 worker 会重建 55 台容器、重启集群上**每一个**模型实例,换零收益),
但「零影响」不成立。

### 7.2.3 网关自身的开销:转发只要 0.1 秒,内容审核要 2.8 秒 `[实测 2026-09-15]`

亲和上线后我注意到一件事:同一个 23k 请求,直连实例 TTFT 2.09s,经网关 3.86s。
**多出来的 1.77 秒不是网络。**

#### 怎么定位的(方法比结论有用)

三步排除,每一步都是可以照抄的判据:

1. **先排除传输。** 用一个**不存在的模型名**发同样大小的 body —— 请求会在进入
   推理前被拒掉,剩下的就是纯传输 + 解析。结果:234 KB body 到网关 **9 毫秒**,
   611 KB **23 毫秒**。传输完全不是瓶颈。
2. **再定位在哪一侧。** 发一个网关请求,同时以 50ms 间隔轮询四个实例的
   `num_requests_running`,看实例**什么时候**开始干活:

   ```
   网关: t=0 发出 → t+2.778s 实例才开始 → 实例耗时 1.57s → ttft 4.25s
   直连: t=0 发出 → t+0.737s 实例开始   → 实例耗时 1.57s → ttft 2.21s
   ```

   **实例侧工作时间两边一模一样(都 1.57s)。延迟全部发生在 new-api 转发之前。**
3. **最后看开销随什么变化。** 按 prompt 大小扫一遍,判断是固定成本还是按量成本。

#### 结论:是内容审核,跟 token 计费无关

| 实际 token | 直连 | 网关(审核开) | 网关(审核关) | 审核占的部分 |
|---|---|---|---|---|
| 576 | 0.353s | 0.600s | 0.418s | 0.19s |
| 2,109 | 0.503s | 1.021s | 0.721s | 0.31s |
| 8,090 | 0.924s | 2.002s | 1.145s | 0.74s |
| 23,148 | 2.092s | 3.857s | **2.190s** | **1.66s** |
| 60,198 | 4.962s | 7.692s | **5.078s** | **2.64s** |

**new-api 真正的转发成本是恒定 0.1~0.2 秒**(鉴权、额度、选渠道、亲和、转发),
不随 prompt 大小变化。剩下的全是 `controller/relay.go:135` 那道转发前的内容审核 ——
它按自己的注释是「进程内 L0 加一次文本模型调用」,那次模型调用要把同样的文本再
prefill 一遍,所以开销随文本长度涨。

**两条被否掉的猜测,都很容易想当然:**

- ❌ **「是本地 token 计数,计费必须计数」** —— 非 OpenAI 模型走
  `service/token_estimator.go:69` 的 `EstimateToken`,一个逐 rune 的状态机。
  40KB 文本 4 万个 rune,Go 里亚毫秒级,不可能是秒。**计费计数跟这事无关。**
- ❌ **「是全文落库(原文 + 归一化 + AES 加密)」** —— `LogQueueSize` 的注释写明
  「异步落库队列长度,满了丢日志而不是阻塞请求」。不在请求路径上。

#### 但它只在首轮贵,后续轮次几乎免费

这是最容易测错的一点。上面那条尺寸曲线**每个请求内容都唯一**,所以每一个都是
「会话首轮」。放到真实多轮回放里:

| 轮 | prompt | 审核开 TTFT p50 | 审核关 TTFT p50 | 差 |
|---|---|---|---|---|
| 0 | 23,088 | 7.04s | 4.28s | **−2.76s** |
| 1 | 23,933 | 0.79s | 0.84s | +0.06s |
| 2 | 24,777 | 1.04s | 0.91s | −0.13s |
| 3 | 25,616 | 1.10s | 0.91s | −0.19s |
| 4 | 26,453 | 0.98s | 0.85s | −0.12s |

后续轮次的 prompt 反而更长(26k > 23k),所以不是「文本短了才便宜」。原因是
`controller/relay.go:164` 传的 `PriorityText: meta.LatestUserText` —— 注释说
「最新一轮用户输入单独给一份,供 L1 优先判定……不必扫完历史与工具返回」。
多轮时 L1 只判新增那一句(约 500 token)。**这个优化是有效的,实测证实。**

所以整体上这是**尾部问题不是中位问题**:

| | 审核开 | 审核关 |
|---|---|---|
| TTFT p50 | 1.04s | 0.91s(−12%) |
| TTFT p90 | 6.93s | **4.24s(−39%)** |
| TTFT p99 | 11.33s | **6.46s(−43%)** |
| 端到端 p50 | 7.06s | 5.97s(−15%) |
| 命中率 | 78.0% | 78.0%(不受影响) |

尾部改善大,因为尾部就是首轮请求。

#### 如果要把首轮那 2.76 秒也拿掉 `[待决策,未实施]`

唯一想得到的真解法:**审核与上游请求并发发起而不是串行**,上游先跑,审核结果没出
之前不把响应交给用户,判 block 就掐掉且不计费。这样 2.76s 藏在 prefill 的 7s 里。

要动 `controller/relay.go:135` 那个「审核必须在预扣费之前」的结构性保证。
**但注意它保证的是「审核拒绝不扣款」,不是「审核必须先于推理」** —— 只要 block 时
不结算、响应不外泄,合规语义保住了,变的只是「可能白算一次 GPU」。这笔账取决于
违规率:千分之几的违规率,换所有首轮请求少等 2.8 秒,是赚的。

**动核心计费链路,不要顺手改。**

### 7.3 让任何请求都变成热请求

| 层 | 手段 | 状态 |
|---|---|---|
| 1 | 会话亲和路由 | ✅ **已上线并验证:命中率 34.1% → 78.4%**(§7.2.1) |
| 2 | `--kv-offloading-size` 卸载到宿主内存 | ✅ 已验证 3.8× |
| 3 | **预热**:收到文档立即发 `max_tokens=1` 预热请求,用户思考时间是免费算力 | 待做,见下面的收益评估 |
| 4 | 跨实例 KV 共享 | 见 §7.4 |

**关于第 3 层预热,收益比标题听起来小,做之前先看清楚:**

- **覆盖面只有 8.4% 的请求。** §7.1 的真实分布:冷 TTFT 中位仅 0.1s,只有 8.4%
  的请求 >20s。对那部分,预热能把 TTFT 从 20~161s 压到约 2.4s(§7.1 的
  「490k 上下文、489k 已缓存 → 2.42s」就是这个状态)。换算成全局:p95/p99 砍掉
  40~50 秒,均值改善约 4 秒,**中位一点不变**。
- **它是延迟优化,不是产能优化,而且满载时为负。** 预热没有减少任何计算量,只是把
  同一份 prefill 提前做掉。集群有空闲时用的是白白浪费的 GPU 时间;**打满时预热请求
  与付费请求抢同一批算力**,还可能白做(用户没接着问、或问的东西让前缀失效)。
  要做的话得加门槛:只在 `num_requests_waiting == 0` 时才发预热。
- **前提是「文档先到、问题后到」。** 赚的是用户思考的那几十秒。若客户端一次 POST
  把文档和问题一起发来,就没有这个窗口 —— 预热等于把一次请求拆成两次顺序执行,
  收益为零、开销为正。**做之前先去 new-api 日志确认首轮请求的形态。**

**但 §3.9.1 之后这笔账要重算 —— 对大上下文,预热不是优化而是前提条件:**

| 上下文 | 首轮 TTFT(冷) | 后续轮 TTFT(命中) |
|---|---|---|
| 32k | 2.59s | ~1s |
| 256k | 25.72s | ~1~2s |
| 512k | 69.06s | ~1~2s |
| **1M** | **200.03s** | **~1~2s** |

**1M 首字 200 秒,任何交互产品都不可能这样卖。** 而命中态是 1~2 秒。也就是说
「1M 上下文」这个卖点能不能兑现,完全取决于那 200 秒能不能挪出关键路径 —— 那正是
预热做的事。上面「只覆盖 8.4% 请求、均值改善 4 秒」的算法**低估了它**,因为它按
全体请求平均;而按 §1.2 的分布,真正用满上下文的那批请求里预热是 0 和 1 的差别。

顺带:审核(§7.2.3)也只在首轮贵。**一次预热请求同时把推理侧和审核侧的缓存都
暖上了,两个 2 秒级/百秒级的首轮成本一起消掉。**

### 7.4 KV 分层的判据:传输必须比重算快 `[实测]`

**每 token 的 KV ≈ 75 KB**(实测:8 卡 × 9.2 GiB 可用 KV 显存 ÷ 1,012,659 token;
与报错「524,288 token 需要 36.6 GiB」算出的 75 KB/token 吻合)。
所以一个平均会话(166.5k token)约 **12.5 GB**,满 1M 的会话约 **75 GB**。

各介质实测带宽,以及搬 12.5 GB 与重算的对比:

| 层 | 实测带宽 | 加载 12.5 GB | vs 重算 |
|---|---|---|---|
| **RoCE RDMA(4×100G 齐上)** | **50 GB/s** | **0.25s** | **50× 快** ✅ |
| **RoCE RDMA(单张 100G,实测 12.2)** | **12.5 GB/s** | **1.0s** | **12× 快** ✅ |
| 宿主内存(PCIe) | ~20 GB/s | **0.6s** | **20× 快** ✅ 已采纳 |
| **NFS**(多流聚合,实测 942~952 MB/s) | **0.95 GB/s** | **13.2s** | **打平/略慢** ❌ |
| NFS(单流,实测) | 478 MB/s | 26s | 2× 慢 ❌ |
| **本地磁盘**(实测) | **109 MB/s** | **115s** | **9× 慢** ❌ |
| 重算 prefill(140k) | 11,370 tok/s | 12.3s | 基准 |

> 🔴 **上表的两行 RoCE 数字会误导,读之前先看清楚**(2026-09-16 纠正):
>
> 1. **「4×100G 齐上 50 GB/s」是 4 × 12.5 的标称推算,不是实测。** §7.5 实测
>    多卡(`--auto_discovery`)只有 **19.61 GB/s**,单轨 12.23 GB/s(已到线速)。
> 2. **两行都只算了 RDMA 那一段,漏掉两次 PCIe 搬运。** GDR 被硬件挡住(§7.5:
>    ACS + 跨 NUMA),所以实际路径是 GPU → 主机内存 → RDMA → 主机内存 → GPU。
>    §7.5 给的端到端账是 12.5 GB 约 **2.2s**,对重算 12.3s 是 **5.6×** ——
>    不是这张表看起来的 50×。
>
> 结论「RDMA 方案成立」不变,但**余量是 5.6~15 倍而非一到两个数量级**,
> 而且是一次 `transfer_engine_bench` 点测,没在真实 KV 搬运路径上验过。
> 引用这张表做任何决策前,请用 §7.5 的端到端数字。

**判据:传输必须比重算快,否则分层是负收益。** 我们重算 140k 要 12.3s,
所以约 1 GB/s 是生死线。这一条排除:

- `ExampleConnector` + 共享文件系统(NFS 打平,无收益)
- LMCache 的 `local_disk` 后端(不论指向 NFS 还是本地盘)
- 任何「磁盘 L3」设想

### 网络拓扑:RoCE 那 50 GB/s 完全没用上 `[实测]`

| 路径 | 带宽 | 当前用途 |
|---|---|---|
| 管理网 `enp131s0f0`(NFS 走这条) | ~950 MB/s | 模型权重、NFS |
| **RoCE `enp194s0f0/f1`+`enp226s0f0/f1`** | **4×100G = 50 GB/s** | 仅传 PP 的 hidden states(每步几十 MB) |

`ip route get <nfs-server>` 确认 NFS 走管理网。**所以跨实例 KV 共享走 RDMA 时
有 50 GB/s 可用,比宿主内存的 PCIe 还快** —— 这使 **Mooncake / NIXL 的离线安装
成为最高价值的工程任务**,而不是可选项。

> 注:这些节点的本地盘(109 MB/s)比 NFS(478 MB/s)还慢,不要想当然。

### 7.4.1 RoCE 健康判据:**不要用 ping** `[实测,一次代价很大的误判]`

**ping 不通 ≠ RoCE 坏。** 本集群每台有 4 个 RoCE IP(全在 `29.165.0.0/16`),
云侧 SDN 只让其中一个回 ICMP,其余三个的 ICMP 在 fabric 里就被丢掉 ——
`tcpdump -i any icmp` 在目标机上**一个包都抓不到**,看起来像是网络坏了。
但 RoCEv2 走 UDP/4791,与 ICMP 是两条完全不同的策略路径。

实测对照(gpu46 ↔ gpu43,以及 gpu46 ↔ 8 台「ping 不通」的机器):

| 轨 | `ping -I <iface>` | `ib_write_bw -d mlx5_N -x 3` |
|---|---|---|
| rail0 `mlx5_0` | ✅ 通 | **11,685 MiB/s**(线速) |
| rail1 `mlx5_1` | ❌ 100% loss(全集群双向) | **11,675 MiB/s**(线速) |
| rail2 `mlx5_2` | ❌ 8 台 100% loss | **11,421~11,686 MiB/s**(线速) |
| rail3 `mlx5_3` | ❌ 100% loss(全集群双向) | **11,679 MiB/s**(线速) |

之前基于 ping 得出的「8 台坏 rail2」「只有 2 条轨可用」「metric 决定可达性」
「SDN 未下发端口-IP 绑定」全部作废 —— 那些是 ICMP 策略的假象。
**那 8 台(gpu2/4/6/7/11/15/16/27)四轨 RDMA 全部线速,完全健康。**

正确的检查方式:

```bash
# 1) 廉价预检:GID 3(RoCEv2 IPv4)存在 + 端口 ACTIVE
for d in mlx5_0 mlx5_1 mlx5_2 mlx5_3; do
  printf "%s state=%s gid3=%s\n" $d \
    "$(cat /sys/class/infiniband/$d/ports/1/state)" \
    "$(cat /sys/class/infiniband/$d/ports/1/gids/3)"
done   # gid3 全 0 = 该轨没地址,这才是真故障

# 2) 权威判据:实打 RDMA(带外握手走管理网,数据面走指定轨)
#    服务端
ib_write_bw -d mlx5_2 -x 3 -F -D 5
#    客户端(<mgmt-ip> 是服务端的 10.0.0.x)
ib_write_bw -d mlx5_2 -x 3 -F -D 5 <mgmt-ip>
```

> 唯一真实存在过的故障是**地址完全缺失**(netplan/NetworkManager 竞态,
> 曾在 gpu1/gpu48 出现 0 个地址)。那种情况下 GID 3 全零,RDMA 真的会断,
> 用上面的预检一眼能看出来。修复:`nmcli device reapply <iface>`(零中断)。
> 另外开机后云侧配置有几分钟延迟,**boot 后至少等 10 分钟再判定**。

### 7.4.2 全量 RDMA 巡检:发现 3 台 5 条轨真坏,重启修复 `[实测]`

> **当前状态(2026-09-14):55 台 × 4 轨 RDMA 全部线速,零故障。**
> 全量复测 112 次(28 对 × 4 轨,覆盖全部 220 个机器-轨组合)全部 ≥11 GB/s。
> 下文保留巡检过程与故障签名,供下次复现时对照。

用 `ib_write_bw` 对 **55 台 × 4 轨 = 220 个组合**做了全量实打(28 对配对,
每台至少作一端)。GID 3 预检 220/220 通过;RDMA 实测结果:

| | 台数 |
|---|---|
| 4 轨全部线速(11.4~11.69 GB/s) | **52** |
| 有轨道 RDMA 不通 | **3** |

坏的具体是:

| 机器 | 坏轨 | 网卡 | 好轨 |
|---|---|---|---|
| **gpu10** | rail1、rail2 | `mlx5_1`/`enp194s0f1np1`、`mlx5_2`/`enp226s0f0np0` | rail0、rail3 线速 |
| **gpu35** | rail3 | `mlx5_3`/`enp226s0f1np1` | 其余三轨线速 |
| **gpu37** | rail2、rail3 | `mlx5_2`、`mlx5_3` | rail0、rail1 线速 |

故障特征(和「ping 不通」那类假象完全不同):

- QP 建得起来、GID 正常交换,**但数据零字节**,`BW average = 0.00` 后挂住
- **双向都不通**(嫌疑机作发端、作收端都是 0.00)
- **换 3 个不同对端复现**(gpu20 / gpu50 / gpu26 / gpu44 全部 0.00),
  而同一台机器的好轨打同一个对端是线速 → 排除对端与配对因素
- 计数器只有 `hw_counters/local_ack_timeout_err`(发出去收不到 ACK)
  和 `req_cqe_error`;`port_rcv_errors`、`port_xmit_discards`、`symbol_error`
  **全为 0**,链路 100 Gb/sec ACTIVE、MTU 8888
- 55 台的 `ecn/roce_np`、`traffic_class`、MTU 配置完全一致 → 不是主机配置差异

**修复:重启,3/3 全部恢复。** 三台重启后 4 轨双向全部线速
(gpu10 rail1/rail2、gpu35 rail3、gpu37 rail2/rail3 均 11.6~11.68 GB/s)。
所以这不是交换机硬件损坏,而是某种会被重启清掉的状态 —— 具体在主机驱动侧
还是云侧端口配置,从主机上无法区分,不做推测。

操作要点:

- **重启后至少等 10 分钟再判定**(开机后云侧配置有数分钟延迟,
  boot+5min 时测会得到假故障)
- gpustack 纳管的业务实例是多节点部署,单机重启不影响服务,
  重启后 gpustack 会自动重建实例(实例 ID 会变)
- 若暂时不能重启,可按坏轨裁剪该机的 `NCCL_IB_HCA`
  (如 `NCCL_IB_HCA=mlx5_0,mlx5_3`),否则 NCCL 会在坏轨上挂死

### 7.5 RDMA 通道实测:可用,但 GPU-Direct 被硬件挡住 `[实测]`

用 mooncake 自带的 `transfer_engine_bench` 在 gpu45 ↔ gpu47 之间实测
(`--protocol=rdma`,metadata 走自带的 HTTP server):

| 模式 | 结果 |
|---|---|
| 主机内存 ↔ 主机内存,单张 100G(`mlx5_2`) | **12.23 GB/s**(线速 12.5,已到顶) |
| 主机内存,`--auto_discovery`(多卡) | **19.61 GB/s** |
| **GPU 显存直传(GDR,`--use_vram=true`)** | **失败:`transport retry counter exceeded`** |

**RoCE fabric 本身健康,坏的专是 GDR。** 原因在硬件拓扑:

```
nvidia-smi topo -m:  GPU0..3 ↔ NIC0..3 全是 SYS
                     (要穿 PCIe + 跨 NUMA 的 CPU 互联)
ACS:                 19 个 PCI 桥中 11 个已启用 —— ACS 会阻断 peer-to-peer DMA
```

`nvidia-peermem.ko`(580.65.06)本来没加载,`modprobe nvidia_peermem` 后
`/sys/kernel/mm/memory_peers/nv_mem` 出现、内存注册那一步过了,但数据仍传不过去
—— 剩下的是 ACS + 跨 NUMA,只能在 BIOS/启动参数层面解(`pcie_acs_override`),
属运维决策。

> **已推翻**:此处原写「`mlx5_1`/`mlx5_3` 全部报 transport retry,只有 2 张卡
> 真正通」。见下面 §7.5.1 —— 那是**跨轨配对**失败被误读成轨道故障。
> 4 张卡都能跑满线速。

**所以跨实例 KV 共享要经主机内存中转**,搬一个平均会话(12.5 GB):

```
GPU → 主机内存 (PCIe ~20 GB/s)   0.6s
    → RDMA (单轨 12.21 GB/s)     1.02s
    → 主机内存 → GPU              0.6s
                       合计 ≈ 2.2s   vs 重算 12.3s  →  约 5.6× 快
```

比 GDR 理想值(~0.8s)差,但仍远优于重算,方案成立。

### 7.5.1 这是 rail-optimized 拓扑:只能同轨对同轨 `[实测]`

用 mooncake 的 `transfer_engine_bench` 在 gpu31 ↔ gpu32 之间逐轨实测
(带外 metadata 走管理网的 `mooncake_http_metadata_server`,
`--use_vram=false`):

| 配对方式 | 结果 |
|---|---|
| `--device_name=mlx5_0` 两端同轨 | **12.21 GB/s** |
| `--device_name=mlx5_1` 两端同轨 | **12.21 GB/s** |
| `--device_name=mlx5_2` 两端同轨 | **12.21 GB/s** |
| `--device_name=mlx5_3` 两端同轨 | **12.21 GB/s** |
| `--auto_discovery`(mooncake 自行配对) | **失败**,读写皆然 |

`auto_discovery` 的报错点明了原因 —— 它尝试的是跨轨路径:

```
local_nic: mlx5_2, peer_nic: ...@mlx5_1 : transport retry counter exceeded
local_nic: mlx5_3, peer_nic: ...@mlx5_2 : transport retry counter exceeded
local_nic: mlx5_3, peer_nic: ...@mlx5_0 : transport retry counter exceeded
Rail paused: peer=...@mlx5_1 error_count=5 pause_ms=30000
```

**第 N 条轨只与对端第 N 条轨连通,轨间无路径** —— 标准的 rail-optimized
组网(每张卡接不同的 leaf 平面,平面之间不互联)。

工程结论:

- **不要开 `--auto_discovery`**,它假设 NIC 之间任意可达
- MooncakeStore 必须显式指定单轨(或给出只产生同轨配对的
  `--nic_priority_matrix`),单轨 12.21 GB/s 已满足 §7.4 的判据
  (搬 12.5 GB 约 1.0s vs 重算 12.3s)
- 之前记录的 `--auto_discovery` 19.61 GB/s 是只有部分轨恰好同轨配对时的读数,
  不是可复现的聚合带宽
- 同理,`NCCL_IB_HCA` 列出多卡本身没问题(NCCL 按 rank 同序配对),
  但任何假设任意 NIC 互通的工具都会在这个 fabric 上失败

### 7.6 Mooncake 的安装:三个坑 `[实测]`

已烘入 `docker/Dockerfile.aarch64_app`。踩过的坑:

1. **不能带依赖装。** `nixl` 的 `Requires-Dist` 含 `torch`,pip 重新解析后开始拉
   `nvidia-nccl-cu13`(206 MB)等,有覆盖 base 里 `2.13.0+cu130`(带 sm_80)的

   torch 建张量 → import mooncake → torch 再建张量全部正常、`arch_list` 仍含 sm_80。
3. **`nvidia.cuda_runtime` 是命名空间包**,`__file__` 为 `None`,取路径必须用

**不需要外部 etcd/redis** —— 轮子自带 `mooncake_master`、
`mooncake_http_metadata_server`、`transfer_engine_bench`、

### 7.7.1 结案:写路径**一直在触发**,是每个 key 都失败 `[实测]`

上面「写路径不触发」的判断是错的 —— 我只看了 master 侧的
`master_put_start_requests_total`,而失败发生在**客户端、RPC 发出之前**,
所以 master 什么也没看到。

vLLM 自己的 `/metrics` 里写得很清楚:

```
vllm:mooncake_store_operation_total{operation="save_exists",status="ok"}              8
vllm:mooncake_store_operation_total{operation="save_put",status="partial_failure"}    8
vllm:mooncake_store_operation_keys_total{operation="save_put"}                      116
vllm:mooncake_store_operation_failed_keys_total{operation="save_put"}                116   ← 全失败
vllm:mooncake_store_operation_bytes_total{operation="save_put"}                29,064,960
```

失败码在 Ray worker 的日志里(**不在 driver 的 serve.log 里**,这是之前漏掉的原因,
要去 `/tmp/ray/session_*/logs/` 找):

```
WARNING [worker.py:1160] batch_put failed: 15/15 keys failed (codes={-800},
        batch_bytes=3559680), first_key=...@pp_rank:0@group:0@875ba951...
```

8 个 rank 全是 `codes={-800}`。

**根因:`batch_put_from_multi_buffers` 传入的是 KV cache 的 GPU 显存地址,
而这套硬件上 GPU-Direct RDMA 不可用。** 逐步实测(gpu41 ↔ gpu42,同轨 mlx5_0):

| 条件 | 结果 |
|---|---|
| `--use_vram=false`(主机内存) | **12.20 GB/s** ✅ |
| `--use_vram=true`,`nvidia_peermem` 未加载 | `Failed to register memory: Bad address [14]` —— 注册就失败 |
| `--use_vram=true`,`nvidia_peermem` 已加载 | 注册通过、QP 连上,**但传输 `transport retry counter exceeded`** |

也就是说 peermem 只解决注册,数据仍然过不去。硬件侧证据:

```
/proc/cmdline           无 pcie_acs_override / iommu 相关参数
lspci -vvv              19 个 PCI 桥,11 个 ACSCtl SrcValid+   ← ACS 阻断 P2P DMA
nvidia-smi topo -m      GPU↔NIC 全为 SYS;GPU0/1 在 NUMA 0,GPU2/3 在 NUMA 2
```

**所以这不是连接器的 bug,是硬件能力缺失。** 三条出路:

1. **BIOS / 内核加 `pcie_acs_override`** 后重测 —— 唯一可能真正打开 GDR 的办法,
   属运维决策(要改启动参数并重启)。跨 NUMA 那一段仍在,收益未知。
2. **改连接器走主机内存中转**(GPU→主机 PCIe,再从主机 RDMA)。
   `--use_vram=false` 已实测 12.20 GB/s,原理成立,但连接器目前不做这一步,
   属引擎开发任务。
3. **放弃跨实例共享,靠网关会话亲和**(§7.2)把同一会话钉在同一实例上。
   本地 KV 卸载到主机内存已有 3.7× 收益(§3),而会话亲和做到之后,
   跨实例共享的价值本来就大幅下降。**这是当前的实际方案。**

> 附带修正:§7.7 表格里「`device_name=mlx5_2`」不是问题所在,
> 换成 `mlx5_0` 并确保同轨配对后,`save_exists` 正常、`save_put` 依旧全失败。

### 8.1 但 V4.1 在 A100-40G 上**跑不起来** `[实测]`

三个相互独立的硬约束:

| # | 约束 | 证据 | 后果 |
|---|---|---|---|
| 1 | **PP 不支持**(其一):KV 共享组不可切分 | `kv_source_layer_ids=[2,8,14,20]` → 层 20-39 是一个 20 层的组;`attention.py:486` `NotImplementedError: PP splits inside a v4.1 kv-sharing group are not supported` | PP4 最均衡只能 `8,6,6,20` |
| 2 | **PP 不支持**(其二):vision MoE 每层都要 `input_ids`,而 PP 跨级只传 hidden_states | `deepseek_v4/nvidia/model.py:1027` `ValueError: DeepSeek V4 vision MoE routing requires input_ids`,报错来自 `Worker_PP1_*` | **只能 PP=1** |
| 3 | **`o_groups=8` 限死 TP≤8** | TP16 时 `8//16=0` → `RuntimeError: shape '[8192, 0, -1]' is invalid for input of size 16777216` | **最多 8 卡** |

8 卡 = 2 节点 = **272 GB 可用**,而 Engram 全卸载后仍需 **307 GB** —— **差 35 GB**。
唯一补法是再开 `--cpu-offload-gb` 把 35 GB 权重也放 CPU,但那要每次前向过 PCIe
流式读 35 GB(~1.75s/步),不可用。

**结论:不是调参问题,是结构性的。V4.1-Flash 在本硬件上无法运行。**

## 9. 4 节点为什么慢,以及为什么不必修

PP4 实测 −65%。三个原因:

1. **DSpark draft 被硬编码成 PP=1**(`vllm/config/speculative.py:1748`、`vllm/v1/worker/gpu/spec_decode/dspark/utils.py:58`)。每个接受周期的 draft 前向只有一个 stage 在工作,PP4 时 **75% 的卡空转**。修它需要改代码。
2. **层切分未为 PP4 调过**。默认 `[11,11,11,10]`,但最后一级还扛着 `lm_head`(5.3 亿参数)和 `dspark_target_layer_ids=[40,41,42]`。推导最优约 `[12,12,11,8]`。
3. 流水线气泡本身是 PP 的固有代价。

**但不必修** —— 想上 4 节点的动机是 KV 空间,而 KV 卸载用宿主内存拿到同样的容量,代价是 0 张卡:

| 扩容方式 | KV 增量 | 代价 |
|---|---|---|
| 2 → 4 节点 | 3.6× | 每卡吞吐 −65%,多占 8 张卡 |
| `--kv-offloading-size` | ~6× | **0 张卡**,淘汰重入 2.79s |
